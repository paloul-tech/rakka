# Rakka Compatibility Policy

This document defines the v1 compatibility rules for Rakka rolling updates. The goal is narrow and explicit: a Kubernetes cluster running release N must be able to roll to release N+1 while routing supported messages, and incompatible nodes must fail closed before they acquire shard ownership.

## Compatibility Dimensions

The v1 compatibility matrix tracks these dimensions together:

| Dimension | Contract |
| --- | --- |
| Crate version | Release artifacts should identify the Rakka crate/package version used by the node. |
| Cluster protocol version | Nodes advertise `ClusterProtocol { version, compatible_with }`; membership admission requires mutual compatibility. |
| Remote envelope version | Network remoting handshakes include the remote envelope wire version. |
| Message schema version | Remote payloads carry `codec_id`, `message_type_id`, and `schema_version`; Protobuf is the default payload codec. |
| Kubernetes manifest version | Manifests carry compatibility metadata through env vars and `rakka.rs/*` annotations. |
| Generated API version | HTTP and gRPC adapter contracts expose stable generated/public API version constants. |
| Agent durable record schema version | Every agent-domain record carries a `StateSchemaVersion`; a binary reads the version it writes and the one before it (`AgentSchemaPolicy`, N/N+1), and fails closed on anything else with `schema-version-ahead` or `schema-version-too-old`. |
| Agent protocol and convention pins | The A2A wire protocol version, the A2A SDK, Rig, the OpenTelemetry SDK, the GenAI semantic-convention revision, and the Collector distribution are pinned, recorded in this document, and held to the manifests and constants by tests. |

The shared fixture lives in `rakka_testkit::compatibility::V1CompatibilityFixture`.

## Allowed Skew

Rakka v1 supports one rolling-update window at a time:

- `N` and `N+1` minor versions may coexist when both nodes advertise a mutual compatibility range, for example protocol `1.0` with range `1.0..=1.1`.
- `N+2`, older-than-N, and cross-major nodes are incompatible unless a dedicated bridge is implemented.
- Incompatible nodes must fail membership admission, fail Kubernetes readiness through `compatibility-not-accepted`, and must not receive shard ownership.
- Message schemas inside a rolling update must be additive. Exact schema policy is reserved for incompatible migrations that require a staged drain, bridge, or separate cluster.

Rakka does not promise arbitrary multi-version clusters in v1.

## Cluster Protocol

Rakka nodes advertise a `ClusterProtocol` with a concrete `ProtocolVersion` and an inclusive `CompatibilityRange`.

- Nodes may join only when compatibility is mutual: each node's range must include the other node's version.
- Kubernetes rolling updates should use an N/N+1 minor-version window, for example `1.0..=1.1`.
- Incompatible protocol changes should use an exact policy and must not allow mixed-version membership.
- Major-version changes are treated as incompatible unless a dedicated compatibility bridge is implemented.

The helper APIs are:

- `CompatibilityRange::n_to_n_plus_one(major, minor)` for rolling-update windows.
- `ClusterProtocol::n_to_n_plus_one(version, base_minor)` for nodes participating in that window.
- `CompatibilityRange::exact(version)` and `ClusterProtocol::exact(version)` for incompatible migrations.

## Remote Protobuf Schemas

Remote envelopes carry `codec_id`, `message_type_id`, and `schema_version`. Protobuf is the default codec, but schema compatibility is still explicit.

- During rolling updates, application message changes must be additive inside the active schema window.
- Additive changes may add new fields with new tags. Existing field numbers and meanings must remain stable.
- Unknown fields may be ignored by older nodes, and missing new fields must have safe defaults on newer nodes.
- Removed fields, changed field types, reused field numbers, changed semantic meaning, or changed required interpretation are incompatible.
- Incompatible migrations must use an exact schema policy, a staged drain, a bridge, or a separate cluster.
- Unsupported schema versions fail closed with typed `RemoteError::UnknownCodec`.

The envelope itself follows the same rule: an optional field with a new tag may
be added to the remote envelope within an envelope version, and the version
(`DEFAULT_REMOTE_ENVELOPE_VERSION`) moves only for a change the additive rules
forbid. Within envelope version 1:

- `ProtoRemoteEnvelope` field 9, `failure`, is a message with `code` at 1 and
  `message` at 2 (the message is bounded to 512 bytes). Fields 1 to 8 are
  unchanged.
- An owner sets it on a reply it could not answer, with the message type id
  `rakka.remote.RemoteFailure`, schema version 1, and an empty payload. The
  asker sees `RemoteRequestError::Rejected { code, message }`.
- An asker on an older binary ignores the field and reports
  `RemoteRequestError::Decode` for that reply instead of a timeout. Its reply
  handler also returns that decode failure to the endpoint, which closes the
  owner-to-asker TCP connection and counts an inbound failure on the asker; the
  owner's peer task reconnects on its next send. So during a mixed-version
  window each rejected ask from an older asker to a newer owner costs one
  connection reset on the asker's side. An owner on an older binary never sends
  the field.
- The carried codes are the entity delivery codes the HTTP and gRPC adapters
  emit (`entity-no-route`, `entity-mailbox-full`, `entity-mailbox-closed`,
  `entity-not-local`, `entity-spawn-failed`, `entity-remote-encode`,
  `entity-remote-send`, `entity-shard-handoff`, `entity-shard-buffer-full`,
  `entity-rejected`) plus `remote-ask-decode`,
  `remote-ask-entity-type-mismatch`, and `remote-ask-unexpected-destination`.
  (`RemoteEntityAskInboundError::code()` also names
  `remote-ask-missing-request-id`, `remote-ask-missing-source`, and
  `remote-ask-invalid-source`, but those failures happen before the owner knows
  whom to answer, so they are never carried.)

The helper APIs are:

- `SchemaCompatibilityPolicy::n_plus_one(current_schema_version)` for standard old/current schema coexistence.
- `SchemaCompatibilityPolicy::additive_window(min, max)` for explicit additive compatibility windows.
- `SchemaCompatibilityPolicy::exact(schema_version)` for incompatible migrations.
- `SerializationRegistry::register_protobuf_compatible::<M>(type_id, current_version, policy)` to encode with the current version while accepting every schema version in the policy window.

Rakka does not automatically diff Protobuf descriptors in v1. Schema compatibility is enforced by the explicit registry policy and by tests owned by the application.

## A2A Adapter Surface

`rakka-a2a` carries several compatibility commitments beyond the remoting envelope:

- The owner remote protocol is versioned. The message type ids `rakka.a2a.A2ARunRequest` and `rakka.a2a.A2ARunResponse`, the JSON codec id `rakka-a2a-json`, the remote schema version, and the protocol version (`A2A_RUN_PROTOCOL_VERSION`) must agree across adjacent node versions; a mismatched protocol version fails closed with a `version-mismatch` owner failure, and an unknown type id or schema version fails closed with `RemoteError::UnknownCodec`.
- The `io.rakka.*` A2A metadata keys (workflow selection, command id/kind, dedup key, causation/correlation, principal, trace context, projection revision, replay cursor, redaction) are public compatibility commitments consumed by clients.
- The agent-collaboration extension is versioned by URI (`urn:rakka:a2a-extension:collaboration:v1`) with the envelope schema number inside it, and its `io.rakka.collaboration` metadata key is a public compatibility commitment. That one key carries **two directions**, and they are told apart by the `schema` field: an *inbound* command envelope always declares it, and the *outbound* echo the task projection writes never does, so an echo replayed onto a send is refused as an echo rather than classified into whichever command cluster its keys happen to trip. The echoed keys are themselves commitments consumed by clients: `delegation`, `parent-task`, `depth`; `handoff`, `handoff-status`, `handoff-target`, `handoff-target-generation`; `team`, `team-claim`, `team-claim-status`, `team-claim-member`, `team-claim-epoch`, `team-claim-generation`; and `conversation-id`, `conversation-status`, `conversation-reason`, `conversation-rounds`, `conversation-turns`. `conversation-rounds` is a **count of rounds that completed**, not the index of the round the conversation ended in: the two readings differ under `RoundsComplete`, which closes the final round before ending. The conversation echo keys its identity `conversation-id` rather than the bare cluster name its three siblings use, because the bare names are the inbound cluster discriminators; the older three predate that rule and cannot be renamed, and any echo added later must follow it. A message that engages the extension half-formed — an unserved version, the declaration without the metadata object, the reserved key without the declaration, an envelope that does not parse under the served schema, or an engagement riding a message that also declares the agent-management extension (executing either command would silently drop the other engagement) — fails closed as `unsupported-operation`; a client that never engages it is untouched. The stable delegation refusal codes (`delegation-skill-unknown`, `delegation-skill-not-authorized`, `delegation-target-ambiguous`, `delegation-skill-not-allowed`, `delegation-invalid-arguments`, `delegation-limit-exceeded`, `delegation-child-conflict`, `delegation-child-mismatch`, `collaboration-version-unsupported`, `a2a-send-executor-missing`, `coordination-tool-not-intercepted`, `goal-tool-not-allowed`) are compatibility commitments surfaced in tool results, effect records, and A2A errors. The envelope carries logical credential-binding references at most, never resolved credentials.
- The coordination-capability authority doors surface three stable codes beside the delegation family. `team-coordination-unauthorized`: a board claim by a member whose durable definition does not grant the `Team` coordination capability resolves refused — the code is recorded in the task's team-claim provenance (`AgentTaskTeamClaimStatus::Refused { code }`) and the board entry reopens for a member that is authorized, so retracting the capability stops claims without parking tasks. `conversation-moderation-unauthorized`: a moderated-conversation operation — a turn, and the moderator's early end, which passes the same door — whose claimed agent's durable record does not *currently* admit it to moderated work; the door requires the definition envelope's `Moderation` grant **and** a lifecycle status that permits dispatch, is consulted strictly after every guard the conversation answers from its own record (so a definitive local refusal such as `conversation-ended` or `conversation-not-participant` never depends on the cross-entity read), and answers on the wire as a definitive `Rejected` decision the caller rebases on. `conversation-participant-record-unreadable`: the moderation door's cross-entity read of the claimed agent's durable record failed; deliberately **not** a domain refusal — it surfaces as a retryable A2A *error*, never a wire `Rejected`, because the very next attempt may serve the read and a conforming caller must not abandon a turn an agents-store fault refused. Doors that previously admitted these operations (a rostered member's claim, a rostered speaker's turn) refuse them from this release on: rosters and board membership are trusted application wiring, never authority sources of their own.
- The team and conversation history-sink faults share the `conversation-participant-record-unreadable` posture: `team-history-backlog`, `team-history-conflict`, `conversation-history-backlog`, and `conversation-history-conflict` are infrastructure faults, deliberately **not** domain refusals — they surface as retryable A2A *errors*, never a wire `Rejected`. A backlog is a full history outbox the courier's next flush drains, and a conflict is a sink write race that can surface *after* the transition committed, so answering either as a definitive rejection would make a conforming caller abandon a command the next drive would admit — or believe an applied one was refused. Releases that answered these codes as `Rejected` predate this classification; clients must treat them as retryable.
- The task-event replay cursor shape `<task-id>:<sequence>` and the stable mapping/projection/handler error code strings are compatibility commitments surfaced in A2A errors and bounded metrics. `RakkaAgentA2AError::code()` forwards the underlying `TaskProjectionError` code (`replay-window-expired`, `invalid-replay-cursor`, `projection-store`, …) rather than flattening every projection failure to the retired `projection` code; clients matching the flat code must move to the forwarded family.
- The agent coordination-event replay carries its own commitments beside the substrate's: the scoped cursor shape `<scope-key>:<sequence>` over `AgentEntityAddress` keys (`task/<tenant>/<id>`, `team/<tenant>/<id>`, `conversation/<tenant>/<id>`, `run/<tenant>/<agent>/<id>`; identity segments may contain `:`, so the sequence is the suffix past the last separator), the two-arm replay answer (a contiguous page, or `WindowExpired` naming the cursor to resume from), the merged `<scope-class>/<source-label>` event kind labels (the scope qualifier is part of the label because the source vocabularies are not disjoint — a task records `task/team-claim-recorded` when it takes a board claim and a team records `team/team-claim-recorded` when it makes one; the terminal-notification labels are `team/team-task-closed` and `task/conversation-terminal-recorded`), and the stable code families surfaced in A2A errors: the `coordination-*` read refusals (`coordination-cursor-malformed`, `coordination-cursor-scope-mismatch`, `coordination-scope-foreign-tenant`, `coordination-scope-unknown`, `coordination-scope-not-replayable`, `coordination-run-events-unavailable`, `coordination-run-events-failed`), the per-log `*-history-window-expired` codes (`task-history-window-expired`, `team-history-window-expired`, `conversation-history-window-expired`), and the run sink's `decision-replay-window-expired`.
- The agents surface adds two read-only authorization operation classes beyond the task-shaped ones: `coordination-event-read` (carrying the addressed scope and the authenticated principal) and `goal-view-read` (carrying the goal and traversal budget; a denial answers the same `None` an absent goal does, by contract). The task-shaped reads carry their authenticated principal the same way `coordination-event-read` does — an explicit parameter on `get_task` and `replay_task_events` — because the wire `tasks/get` shape has no metadata channel for one; a deployment authorizer may therefore require a principal on `GetTask`/`SubscribeToTask` without cutting off the deployment's own typed client.
- The `io.rakka.principal.ref` key has two accepted spellings, and the choice between them is now a commitment: the compact `type:id[:display]` string — kept byte-identical for every principal whose components are colon-free — and the JSON object (`{"type", "id", "displayName"}`), which is the only spelling that can carry a colon-bearing component (a SPIFFE URI, an ARN, an OIDC subject) without ambiguity, because the string form's `splitn` decoding cannot tell `("user:a", "b")` from `("user", "a:b")`. Rakka's own encoders — the typed client, the delegation and handoff executors — switch to the object form exactly when a component contains a colon; durable provenance strings follow the same rule (compact join, or canonical JSON object, which no legacy join can collide with). Clients emitting colon-bearing ids through the string spelling get whatever `splitn` yields — the historical behavior — and should move to the object form.
- A team command's durable deduplication identity binds the decision's own content: the derived operation id covers the tenant, team, verb, a canonical digest of the whole cluster, and the caller's deduplication key. A pure retry — same key, same cluster — converges on the recorded decision exactly as before; two *different* decisions under one reused key derive two operations instead of the second being answered from the first's memo (previously a `Duplicate` echo of a decision the board never made). Callers that relied on a reused key to absorb *changed* payloads were already off-contract — the conversation arm's coordinate-derived ids and the handoff arm's forced discriminator have always refused that shape. A management message carrying the `io.rakka.agent.result` binding is refused whole (`unsupported-operation`), exactly as one carrying the collaboration cluster is: executing the management command would silently drop the submission.
- The collaboration command surfaces answer stable kebab-case refusal codes, and the families are compatibility commitments even where a member is not individually listed: the task's handoff door and the in-process send executors answer `handoff-*` (`handoff-conflict` — an unresolved transfer another identity owns; `handoff-not-held`/`handoff-forged` — a result notice no cell matches, definitive for the exchange; `handoff-identity-mismatch` — a cluster that does not deduplicate under its own handoff id; `handoff-not-agent-owned`, `handoff-source-not-current`, `handoff-limit-exceeded`, and the structural `handoff-context-invalid`/`handoff-request-too-large`; `a2a-handoff-executor-missing` when no executor is wired); the board's claim arbitration answers `team-claim-*` (`team-claim-stale-epoch` — the epoch fence against courier-reordered stale decisions; `team-claim-already-owned`, `team-claim-wrong-team`, `team-claim-task-unknown`, `team-claim-limit-exceeded`, `team-claim-forged`) beside `team-state-too-large`; the conversation's turn protocol answers the `conversation-*` vocabulary (the coordinate and ownership fences `conversation-turn-out-of-order`/`conversation-not-your-turn`/`conversation-turn-superseded`/`conversation-turn-content-mismatch`, the ceilings `conversation-rounds-exhausted`/`conversation-turns-exhausted`/`conversation-message-too-large`/`conversation-turn-usage-too-large`, the direction rules `conversation-direction-required`/`conversation-direction-forbidden`/`conversation-designate-unknown`, and the end fences `conversation-end-not-permitted`/`conversation-end-not-moderator`/`conversation-end-stale-round`); and a typed-result submission naming an agent-owned task answers `task-not-human-owned`. Codes in these families are frozen once shipped; new members may be added, and a client must treat an unknown member of a known family as a definitive refusal of that command, not a transport fault.
- Conversation budget exhaustion answers `conversation-budget-exhausted` — the exhausted dimension rides the human-readable detail, never the code. (A pre-release build answered the bare dimension label, `tokens`, as the code; nothing shipped under that spelling.) Two creation-door commitments beside it: `conversation-completion-unreachable` refuses any configuration with no road to a terminal state — under moderator-decides, forbidding the early end with no deadline; under all-rounds, a finite token grant with the early end forbidden and no deadline, because exhaustion refuses rather than parks and would bar the final round forever — and `conversation-operation-id-too-large` refuses a command whose operation id exceeds the entity's admission cap (`AGENT_CONVERSATION_OPERATION_ID_MAX_BYTES`, 1 KiB), the guard that keeps the creation door's per-entry byte reserves a genuine upper bound; every id the coordination derivations mint at maximal legal segments passes it.
- Two stable codes guard the task's board and dependency contracts. `task-team-not-agent-owned`: a creation pairing a human-owned definition with a team binding is refused at the door — the board exists to name the agent that serves a task, and admitting the pairing would strand every claim `Initiated` forever; a claim reaching a record persisted before this door answers the registered `team-claim-wrong-team` instead of a fresh code, because deployed boards enumerate the claim codes they may settle and a code they do not know would leave the claim exchange re-driving forever. `dependency-registration-receipt-undecodable`: the dependent's classification of an *accepted* registration receipt its binary cannot decode — recorded on the outstanding exchange and the unsettleable-exchange metric, never on the wire — so a receipt that may carry an already-terminal upstream's outcome is re-driven until a binary that can read it settles it, instead of settling into a durable guess. In the same classifier, a refused `task-state-too-large` registration is now *outstanding* rather than definitive: the upstream's terminal transition drops the growth reserve that refused it and the terminal-answer path precedes the bounds check, so a re-drive is answered with the true outcome; clients observing the dependent must expect `Blocked` (the documented stuck-dependency posture) where they previously saw a resolved-failed edge.
- `task-dependency-limit-exceeded` is a *definitive* refusal of a team claim and an *outstanding* one of a dependency registration, and the split is a commitment rather than an inconsistency. Both are the same exit of the task's bound check — the one that fires when a definition refresh lowered `max_dependencies` under a record already holding more edges than that — but the exchanges reach it differently. A claim never touches the dependency map and a terminal task is already answered under `team-claim-task-terminal`, so no re-drive can change the answer: the board settles the entry rather than parking it `Pending` and unstealable forever. A registration is answered by an *already-terminal* upstream with its outcome receipt before the bound is consulted at all, so the upstream's own terminalization turns the refusal into a real answer and the edge stays outstanding. The rule both follow: a bound the exchange can never satisfy is definitive; a bound it merely has to wait out is not.
- `handoff-task-terminal`: the resolution code of a handoff the task's terminal transition settled because the task ended while the transfer was still unresolved. A pending transfer must not cross the terminal boundary unresolved — the owed handoff result derives only from a settled provenance, so an `Initiated` cell surviving the terminal would strand the fenced source run forever. A result accepted from the transfer's own minted generation settles the provenance `Accepted` (the target durably held responsibility; its acceptance reply may still be in flight); every other terminal flavor settles it `Refused` under this code, which reaches the source run through its handoff-result notice and resumes it exactly as any other definitive resolution does.
- Slice 6.2 adds two stable refusal codes and changes what one existing code *carries*, without changing the code itself. `guardrail-chain-mismatch`: a deployment attesting through `AgentToolAuthority::with_memory_ingress` that its run memory evaluates the memory-ingress boundary under the authority's own chain, whose two chains declare different evaluations. It takes the `AgentRunMemory` rather than a bare `AgentMemoryRetrieval`, because the object attested must be the object the run assembles through — a bundle handed in for the occasion proves only that a matching chain exists somewhere — and a memory carrying no retrieval bundle is refused under the same code, as is an authority with no chain attesting one (two absences are not an agreement). `AgentToolAuthority::attests` re-checks the claim against a memory assembled elsewhere. It is a **wiring-time** refusal, not a dispatch one — a misconfigured deployment fails at startup — and the comparison is a *declaration digest* (revision, policy reference, and each stage's id, revision, boundary set, and mandatory flag), never the rule objects, which have no equality. Comparing declarations rather than revisions is what catches the shape a deployment actually lands in: an empty bundle chain carrying the same revision number as the authority's populated one. A deployment that does not attest is not silently unprotected — the authority stops counting the memory-ingress boundary, so an envelope requiring a memory-ingress-only stage refuses dispatch with the already-registered `guardrail-stage-unevaluated`. `execution-policy-required`: an opt-in refusal, off by default, of an intent that names no `AgentExecutionPolicyRef` at a deployment that has called `with_required_execution_policy`; specification 11.8 says an intent *SHOULD* carry one, so the permissive default is unchanged, and this is the switch that makes a workload-isolation claim checkable rather than asserted. It is definitive rather than transient: no worker will ever accept a class that does not exist. The requirement covers *every* intent, not only tool calls — a model call, a compensation, an A2A send and a workflow start all reach a worker the same way — so `with_required_execution_policy(substrate)` takes the class the substrate's own effects run under, which `AgentToolAuthority::effect_policies` stamps onto them (`AgentEffectPolicies::with_substrate_execution_policy` for a hand-assembled policy set). Registered tools keep taking their class from their binding declaration, and an unclassified one is what the switch exists to refuse. A deployment enabling it must ensure its router accepts the substrate class and some worker serves it. And `credential-resolution-failed` keeps its code, its attempt accounting, and its place in `AgentRunEffectOutcome::Exhausted` — what changed is that the *detail* beside it is now Rakka-authored, naming the logical `AgentCredentialBindingRef` rather than interpolating the application resolver's own failure text, which was reaching the durable outbox row and the dispatcher fleet index verbatim. Every persisted attempt detail is now truncated at `AGENT_DISPATCH_FAILURE_DETAIL_MAX_LENGTH` (512 bytes, single line), and that bound describes the *record*, not one half of it: an application-supplied stable code is bounded separately and tighter at `AGENT_DISPATCH_FAILURE_CODE_MAX_LENGTH` (128 bytes) so a verbose code cannot crowd the detail out of a line they share, and the composed `code: detail` line is bounded again. A code longer than 128 bytes is truncated, which by construction leaves a string equal to no registered code. The bound itself is declared once, by the substrate that owns the records it protects (`rakka_agent_workflow::AGENT_DISPATCH_LAST_ERROR_MAX_LENGTH`), and applied at each durable write rather than at each caller: `AgentDispatchEntry::last_error_code` — one field on the single fleet-index record every worker loads and re-persists on every claim pass — bounds whatever any writer hands it, including a telemetry event a caller built by hand. Clients parsing the tail of a long collaborator error must not rely on it surviving.
- The first post-Phase-6 gap slice adds one stable refusal code, one command field, and one segment class, and changes what one existing code can carry. The `ToolResponse` guardrail boundary now has an evaluation point (`AgentToolAuthority::review_tool_response`, in the dispatcher after execution and before delivery), so `AGENT_EVALUATED_GUARDRAIL_BOUNDARIES` and `AGENT_AUTHORITY_EVALUATED_GUARDRAIL_BOUNDARIES` both include it: a deployment whose envelope required a stage bound only to that boundary, which previously refused every dispatch with `guardrail-stage-unevaluated`, now dispatches and evaluates the stage. The boundary answers the already-registered `guardrail-blocked` (now also a *determinate* failure of an effect whose tool did run — the result is refused, the effect fails once, the target is never re-invoked), `checkpoint-required` (fail-closed: no checkpoint can gate a response that already exists), `guardrail-transform-unsupported` (a transform of reference content), and `guardrail-transform-invalid` (a transform that does not form a bounded inline result), plus the new `guardrail-content-unencodable` for a result whose artifact reference does not encode. `AgentRunEntityCommand::ResolveCheckpoint` and `::ResolveIndeterminateEffect` gain a `telemetry: AgentTelemetryContext` field (`#[serde(default)]`; commands are JSON-encoded, so one encoded before the field decodes to the empty context) carrying the incoming request's trace context — observability only, never read by resolution. `AgentSegmentOperation::CheckpointResolve` (`checkpoint-resolve`, `rakka.agent.checkpoint.resolve`, `INTERNAL`) joins the bounded segment vocabulary; `AgentTelemetrySegment` gains `span_id`, a durable span identity a segment exports under verbatim; and `rakka.agent.link.kind` gains four values (`parked-checkpoint`, `resume-request`, `ambiguous-attempt`, `reconciliation-decision`), catalogued in `AGENT_TELEMETRY_LINK_KINDS`. `AgentCheckpoint::telemetry` now stores the parked span's own identity rather than the run's context; a record persisted before this decodes as before, and no reader treats the field as correctness.
- The second post-Phase-6 gap slice ("the memory and claims write side") widens the wind-down exemption of the definitive-failure arm and changes nothing about which code the arm answers. A definitively failed or exhausted `ClaimAppendCall` now leaves the run it belongs to live, exactly as a failed `MemoryPromotionCall` and a failed `GoalEvaluationCall` already did: the failure stays on the effect record under the executor's code, no `EffectFailed` terminal reason is recorded, and the initiator re-issues the append under a new operation id (specification 13.4). A deployment that relied on a refused claim append to *end* a run — nothing shipped issues `AppendClaim`, so none is known — must now cancel the run explicitly. Two durable records gain tool provenance, additively: `AgentToolResult` (in the loop state, `agent-loop-state`) and `SessionMemoryEntry` (`agent-session-memory-entry`) each gain `tool: Option<AgentToolId>` and `effect_id: Option<AgentEffectId>`, both `#[serde(default)]` and both still at schema version 1 — a record persisted before the fields decodes with `None` in each, and a stamped record's entry id, operation id, and content digest are byte-identical to an unstamped one's, because neither field enters any derivation. The run writes them for the `ToolResult` role only, from the effect record that names the model's call, and `None` for every other role; `source` keeps the call id unchanged. The PostgreSQL session store JSON-encodes the whole entry into its existing `entry BYTEA` column, so there is no DDL and no migration. Both fields are provenance, never authority: nothing resolves or infers from them, and the memory conformance suite gains one clause (`session_tool_provenance_round_trip`) holding every backend to carrying them through unchanged. `AgentMemoryPromotionRequest` gains `roles: Option<Vec<MemoryEntryRole>>` (`#[serde(default)]`; a request persisted or sent before the field decodes to `None`, which promotes every entry in the window — the previous behaviour, unchanged). With `Some(set)` the executor promotes only the window's entries whose role is in the set; the `1..=64` window bound is checked at commit as before and the selected count is held to the same bound in the executor. Two stable codes come with it: `memory-promotion-selection-empty`, the executor's *definitive* refusal of a window that selects no entry (the effect fails once under it, nothing is written, the run stays live — a silent empty success would have let a caller believe a window was promoted), and `run-memory-roles-empty`, the run's door refusal of an empty role set, which can select nothing whatever the window holds. `memory-promotion-selection-invalid`, already answered by the executor for an unsizeable selection, is now also its answer to a selected set past the bound. A consolidation still needs exactly one *selected* entry: a one-entry window whose entry the filter excludes answers `memory-promotion-selection-empty` and leaves the target untouched. Provenance and idempotency are unchanged: the promoted identity is per entry, so a filtered promotion converges on the same records an unfiltered one wrote. **The post-terminal memory window.** A run that has ended `Completed`, `Failed`, or `Cancelled` now accepts `PromoteMemory` and `AppendClaim` for `AgentEffectPolicies::post_terminal_memory_window_ms` after its terminal stamp (default `AGENT_POST_TERMINAL_MEMORY_WINDOW_DEFAULT_MS`, 600 000; builder `with_post_terminal_memory_window_ms`; not a durable field — the policies are deployment configuration projected at registration, so there is nothing to serde-default); `0` closes the window and restores the previous `run-terminal` refusal. Past the window, or on a terminal record that carries no `terminal_at` (persisted before schema version 2 and never repaired — measuring from `updated_at` would make a sliding clock, since every accepted post-terminal command moves it), both commands answer the new stable code `run-memory-window-closed`; `HandedOff` and `Superseded` answer `run-terminal` whatever the window. Both commands are also accepted *during* a wind-down: `AgentRunEffectKind::exempt_from_wind_down_fence` now covers `MemoryPromotionCall` and `ClaimAppendCall` beside `CompensationCall` and `WorkflowCancelCall`, so a promotion or claim committed on a live run that then winds down still dispatches (previously it was cancelled in place by the fence), the two registered codes `run-memory-promotion-fenced` and `run-claim-append-fenced` are no longer answered by anything (their variants stay so a matcher still builds), and a terminal run's settle pass flushes the exempt kinds instead of nothing. The effect rides the run's ordinary outbox and is claimed by the ordinary dispatch pass — the dispatcher's wind-down sweep skips exempt kinds and never re-fences them — so **an application that stops pumping a terminal run's outbox never dispatches a post-terminal effect**; nothing upstream drives it. Its outcome is applied to the terminal record without moving status, phase, terminal reason, or terminal stamp: `RecordEffectResult` on a terminal run now accepts a result for an exempt-kind effect and answers `run-terminal` for every other, exactly as before. An `Indeterminate` outcome delivered to a run that has ended opens a reconciliation checkpoint for these two kinds, as a live run's does (both kinds are idempotent by default and the dispatcher retries an ambiguous attempt under the generation's key; the one path that can still park one is a possibly-executed attempt whose recovery retry the authority refused, and since issue #120 that park holds a checkpoint answerable by `ResolveCheckpoint` or `ResolveIndeterminateEffect`). The effect reserves and settles its attempts against the run's own budget as any generation does and can still be `run-memory-promotion-unaffordable` / `run-claim-append-unaffordable`; the task's escrow settlement, folded at the terminal transition, is not re-taken. Once the run's session memory has been purged a post-terminal promotion exhausts on the retryable `memory-promotion-source-missing` and, being exempt, ends nothing. **Effect identity within a turn** (`agent-loop-state`, still version 1): `AgentLoopState` gains a serde-defaulted per-turn slot counter that `clear_turn` does not reset. The previous allocator counted only the effects still held, so a promotion or claim append committed after a turn's resolved effects were dropped — a run resting on its result proposal, or a run that has ended — derived the identity of the turn's resolved model call and was answered `Duplicate` from the operation log forever; a record persisted before the counter decodes it as zero and keeps the held effects as a floor, and the two handlers additionally skip any slot whose first-generation result the run's operation log already holds. The residual: a pre-counter record whose terminal turn's results have since been evicted by sixty-four later operations on the same run — unreachable at this pin, since nothing shipped issues either command. `AgentModelRequest` gains `telemetry: AgentTelemetryContext` (`#[serde(default)]`; a request built through `new` or encoded before the field decodes to the empty context), the run's own durable trace context — the context the model effect was committed under, which the real dispatch pipeline and the testkit's in-process driver both stamp from the intent — so a model adapter may parent its provider span on the run's trace instead of rooting its own; observability only, never read for inference, and the precedent is the `telemetry` field `ResolveCheckpoint` and `ResolveIndeterminateEffect` gained in gap slice 1. `DeterministicModelAdapter::requests` (testkit) records every request the adapter produced a turn for. `rakka-a2a` re-exports the A2A SDK's `ServiceParams` at its root under the `server` feature (which `agents` implies), reachable as `rakka::a2a::ServiceParams` under the facade's `a2a-server` or `a2a-agents` feature — additive; it is the one constructor input a `RakkaA2AServiceBuilder::request_observer` callback receives, and an application that named it through its own `a2a-server-lf` dependency can drop that dependency. `AgentDispatchAuthority::review_tool_response` loses its default body — **breaking for implementors, additive for callers**: every implementation of the trait must now state what it does at the `ToolResponse` boundary, because a wrapping authority that forgot to forward the method silently dropped the evaluation point gap slice 1 wired, and a compile error is the right failure for that omission. `accept_tool_response_unchanged` is the documented one-line body for an authority that evaluates no response chain (the previous default's behaviour, made explicit); a wrapper forwards to the authority it wraps. The pipeline's behaviour at the boundary, and every registered code it answers, are unchanged.
- The third post-Phase-6 gap slice ("the turn rest") changes which effects a turn waits on and adds no code, no field, and no schema version. Every site that decides a turn is over — the `Tool`, `A2aSend`, `A2aHandoff`, and `WorkflowStart` outcome arms of `RecordEffectResult`, the handoff-refusal exchange, the definitively-failed handoff-send arm, the two group-member failure arms (a delegation send or a workflow start that failed to create its child), and `turn_rest` itself — now consults `AgentLoopState::awaits_turn_effect`, which counts every outstanding effect except a `MemoryPromotionCall` or a `ClaimAppendCall` (`AgentRunEffectKind::outside_the_turn`: exactly those two, because each copies work the turn already recorded and resolves through an arm that moves neither phase nor status; a compensation, a workflow cancel, and a goal evaluation stay inside the count). Previously the kind-blind `awaits_effect` decided the rest, so a promotion or a claim append outstanding when a turn's last result landed held the turn open and left the run parked `AwaitingTools` with zero outstanding effects, no wake, no terminal reason, and `can_advance` false — permanently. `awaits_effect` keeps its kind-blind meaning and stays public; the quiesce condition, the handoff planning fence, the budget's concurrency reservations, and the pending-effect bound still count every kind on purpose. A consumer changes nothing: `PromoteMemory` and `AppendClaim` may now be issued into a live run whatever its turn holds in flight, and the post-terminal window, the wind-down exemption, and every registered code are unchanged. **Repair of a record already wedged.** A record a binary before this slice left in that shape — `AwaitingTools`, no effect of the turn outstanding or ambiguous, the run neither winding down nor parked on a checkpoint, reconciliation, suspension, or top-up wait (`AgentRun::needs_turn_rest`) — is rested by the next settle pass that touches it, exactly as the last result would have rested it (`RecordingTurn`, or `AwaitingChildren` on a closed group), and the pass then folds the turn and carries on. Any command's apply and any sweep drives that pass, so a record whose promotion resolved before the upgrade heals the same way as one whose promotion is still outstanding, and no operator action is needed; a record that is suspended, winding down, or parked on a reconciliation decision heals when that wait's own resolution runs the pass. The repair writes only a phase and a status an N binary already knows, so it carries no rollout order; during a rolling update an N binary can still wedge a run, and that record heals on its first N+1 settle.

- Phase 7 slice 7.7 ("MCP client") adds a new adapter-tier crate, `rakka-agent-mcp` (facade feature `agent-mcp`), fifteen stable refusal codes, and three additive `rakka-agent` surfaces, and changes no existing durable schema; the one record it adds, the stored `McpDescriptorSet`, carries its own `schema_version` (`MCP_DESCRIPTOR_SET_SCHEMA_VERSION` = 1), and a decode refuses a version newer than the build knows. The codes, each with every case that raises it. `mcp-tool-error`: the MCP server's own `isError: true` answer — its first text block with the attempt's credential material replaced by `<redacted>`, then flattened to one line (control characters, U+2028/U+2029, and the bidirectional formatting controls become spaces) and bounded at 512 bytes; it may contain what the tool said, never the call's arguments — and also call arguments that are not a JSON object, an inline result `AgentTaskContent::inline` refuses, and a result that cannot be re-encoded. `mcp-input-required`: the server's `input_required` (MRTR) result, a determinate refusal in this phase, since there is no mid-call resumption. `mcp-protocol-unsupported`: no version the binding lists is one the server shares — `server/discover` found none, the legacy `initialize` fallback was refused for its version (JSON-RPC `-32022`), or the legacy handshake answered a version the binding does not list — and also a task-augmented result (`CallToolResponse::Task`) or any response kind rmcp adds later, neither of which this client requests. `mcp-result-too-large`: a result whose content exceeds the inline bound while the binding's `result_behavior` does not permit an artifact reference. `mcp-hint-contradicts-declaration`: with `honor_hints`, a `destructiveHint: true` or an `idempotentHint: false` against a tool declared `ReadOnly` or `Idempotent`, or a `readOnlyHint: false` against `ReadOnly`; a `readOnlyHint: true` silences the other two (in MCP's own semantics they are meaningful only when `readOnlyHint` is false), and a hint never changes a declaration. `mcp-peer-agent-channel-refused`: a server whose reported `serverInfo.name` — from the `initialize` result, or from a `server/discover` result's `_meta` — starts with `rakka-agent` (MCP is never an agent-to-agent channel, specification 14.4), checked at descriptor sync and at every dispatch attempt alike; a server that reports no `serverInfo` reads as an empty name and passes, because the rule is written for a cooperative threat model — a Rakka agent served over MCP identifies itself — not against a server that hides what it is. `mcp-transport-unsupported`: `McpDispatchToolExecutor::new` refusing a `ChildProcess` binding (only `with_launcher`, which takes the launcher with the bindings, admits one), and a deployment launcher's own refusal (`McpLaunchError`: the launch specification unreadable, the spawn failed, or child processes unsupported); an HTTP binding handed to the launcher-path sync is `mcp-descriptor-sync-failed`, not this. `mcp-descriptor-schema-too-large`: an input or an output schema over 64 KiB (`MCP_DESCRIPTOR_SCHEMA_MAX_BYTES`). `mcp-descriptor-sync-failed`: a transport or protocol failure inside `sync_mcp_descriptors`/`sync_mcp_descriptors_over` not covered by a more specific code, including a `tools/list` that has not ended after `MCP_LIST_PAGES_MAX` (64) pages and a binding handed to the sync for the other transport (an HTTP binding over a launched transport, or a child-process binding to the HTTP sync). `mcp-binding-invalid`: a `McpServerBinding::validate` refusal — an empty tool list, a `max_attempts` of zero, an unknown or malformed protocol version, a URL that is not `http`/`https` or carries userinfo, a fragment, or whitespace, a tool name whose derived id is invalid, a credential binding paired with a `ChildProcess` transport at the server or at any tool, or a tool declaration naming a credential binding other than the server-level one — and also an invalid server id (refused by `McpServerId::new` and on decode), the executor's construction refusals (a server registered twice, a binding with no synced set or a set with no binding, an allow-listed tool with no synced descriptor) and a sync against a server that no longer lists an allow-listed tool. `mcp-tool-unbound`: a call naming a tool the executor holds no route for. `mcp-credential-material-unsupported`: a resolved credential whose material cannot become an HTTP header (`Basic`/`Custom`, or an API key whose name or value is not a legal header), and any credential that arrives for a child-process attempt, refused before the launcher runs. `mcp-credential-missing`: an HTTP binding that names a credential binding — on the server or on the tool's declaration — and an attempt that carries no resolved credential, refused before any client exists; the message names the binding reference and nothing else. `mcp-transport-failed`: every other transport- or protocol-level failure, including the whole attempt — connect, the recheck's `tools/list`, the call, and result mapping — running past its one shared deadline, which is the effect's own `timeout_ms` or, for an effect that committed none, the executor's default (`MCP_ATTEMPT_TIMEOUT_DEFAULT_MS` = 30 000 ms, `with_attempt_timeout_default_ms`); a failed `Auto` lifecycle reads `LegacyFallbackFailed(discover: …; fallback: …)`, naming both phases by variant; this is an `AgentDispatchError::Invocation` and is recorded as the error code itself, never wrapped. `tool-descriptor-revision-mismatch`: the executor's dispatch-time recheck against the descriptor's own `schema_digest`, refusing a call whose live input schema has changed since sync, and refusing (uncached) an attempt whose `tools/list` has not ended after 64 pages; the listing is cached under an executor-chosen TTL (`with_descriptor_recheck_ttl_ms`, default `MCP_DESCRIPTOR_RECHECK_TTL_DEFAULT_MS` = 60 000 ms; `0` rechecks on every attempt) rather than the listing's own `ttlMs`, which would let the server decide how long a reshaped schema stays trusted — specification 11.8's "recovery MUST NOT silently execute against a materially different schema" made concrete for MCP tools, within that TTL. Every dispatch-time code above but `mcp-transport-failed` reaches a caller through `AgentDispatchError::Collaborator` (the sync's own codes reach one through `McpSyncError`), whose own `code()` is always the pipeline's `dispatch-collaborator-failed`; the inner MCP code — and a deployment's own egress-refusal code, for which Rakka registers none — rides the bounded `code: message` line composed onto the outbox row's and the fleet index's failure detail, never the pipeline code itself, and since slice 7.10 it is also recorded, once the retry budget is spent, as the failure's reason on the effect record and, when the failure ends the run, on `EffectFailed`. ## Agent Domain

The agent domain — `rakka-agent-workflow`, `rakka-agent`, `rakka-agent-postgres`, `rakka-agent-knowledge-graph`, `rakka-agent-knowledge-graph-postgres`, and the `rakka-a2a` `agents` feature — adds compatibility commitments of its own on top of the A2A adapter's above. The tables in this section are held to the code by `cargo test -p rakka-agent --features otel --test compatibility_currency`, for the knowledge graph's two record rows by `cargo test -p rakka-agent-knowledge-graph --test compatibility_currency`, and for the A2A protocol row by `rakka-a2a`'s own unit tests — each crate holds the rows whose constants it can see: a row that disagrees with a constant or a manifest fails validation, in either direction, and a table carrying two rows for one record fails too.

### Durable records under N/N+1

Every persisted agent record carries its schema version, and the version is checked on the load path rather than trusted:

- The default policy is one rolling-update window: a binary reads the version it writes and the version immediately before it (`AgentSchemaCompatibility::n_plus_one`, one window per `AgentRecordKind` in `AgentSchemaPolicy`). A record from a newer binary fails closed with `schema-version-ahead`; a record older than the window fails closed with `schema-version-too-old`. Neither is ever read with guessed semantics. The check runs wherever a record leaves a store: the entity load and recovery paths check the entity record and every versioned record nested in it with its own version — the definition, settings, and admission decision inside an agent; the task definition, wake policy, goal specification, escrow ledger, and pending history inside a task; the loop state and its pending turn, effects, open checkpoints, and session outbox inside a run; the pending history inside a team or conversation — before it materializes. The memory stores check each entry, snapshot, and private-memory record they return. The append-only logs are checked where their read contract hands them out: the coordination replay entry point (`AgentCoordinationSources`, and the four `replay_*_coordination_events` functions it fronts) refuses a task, team, or conversation history entry or a decision event outside the window with the same two codes, and the session view treats such a decision event as a sink outage — its durable half stays authoritative and its projection half reports itself unavailable. A durable store implementation that deserializes these records may check earlier; it is never the only check.
- The knowledge graph applies the same window to its two record kinds locally (`ClaimError` answers the same two codes), so a graph backend and the agent domain share one posture without a dependency between them.
- A bump is additive within the window: a record written before the bump keeps its old version and both generations round-trip it losslessly, so no live entity is stalled by a rollout. A record acquires the new version only when a transition rewrites it, which is what makes the N binary's fail-closed on an N+1 record the safe direction — the field it cannot see is one it would otherwise erase.
- Deploy the N+1 binaries fleet-wide before running any one-time repair that rewrites records at the new version (see the run state's backfill below); a repaired record is an N+1 record.
- The inter-entity exchange protocol is versioned at the codec layer as well as in the record: codec id `rakka-agent-json`, message type ids `rakka.agent.ExchangeEnvelope` and `rakka.agent.ExchangeReply`, and `AGENT_EXCHANGE_REMOTE_SCHEMA_VERSION` (1) are commitments adjacent node versions must agree on, registered with an exact policy, so an unknown envelope version fails closed with `RemoteError::UnknownCodec` before any entity sees it.
- The A2A agent extensions carry their version in the URI (`urn:rakka:a2a-extension:agent-management:v1`, `urn:rakka:a2a-extension:collaboration:v1`) with the envelope schema number inside (`AGENT_MANAGEMENT_SCHEMA_VERSION`, `AGENT_COLLABORATION_SCHEMA_VERSION`, both 1); a version the receiving node does not serve is refused as `unsupported-operation` rather than interpreted.
- Two adapter semantics versions sit beside the schema versions and are deliberately not schema versions: `CURRENT_AGENT_LOOP_ADAPTER_VERSION` (the meaning a model adapter gives the turns a loop-state record carries; a Rig upgrade that changes request, tool-call, message, or serialized-run semantics moves it as an explicit migration, never a silent reinterpretation) and `AGENT_GENAI_CONVENTION_REVISION` (the telemetry mapping; its upgrade is a specification 17.20 review and never a durable-state migration).

The records above version 1, and what each bump requires of a rollout:

- The durable agent run state (`AgentRecordKind::RunState`) is at schema version **2**. Version 2 carries `AgentRun::terminal_at`, the clock short-term memory retention is measured from. Under the N/N+1 policy a version-1 binary fails closed on a version-2 record rather than loading it — which is the point: serde drops a field it does not know, a terminal run keeps accepting settlement and return commands, and the stamp is written exactly once under an already-terminal guard, so an older peer that loaded such a record would erase the stamp with no way to restore it and the run's session rows and snapshots would never be purged. A record created before the bump keeps saying version 1 and both generations round-trip it losslessly, so no live run is stalled by the bump; it upgrades its own stamp at the terminal transition, which is what gives it the version-2 field. Deploy the version-2 binaries before relying on retention discharge.
- **Runs that were already terminal when version 2 shipped need a one-time repair.** The stamp is written under the already-terminal guard that makes it once-only, so a run that had already reached a terminal status never re-enters the transition that would give it one: its retention is refused (`terminal-time-unknown`) permanently, and its session rows and context snapshots are never purged. `AgentRunTerminalStampBackfill` (`rakka-agent`) stamps those records from their own `updated_at`, which for a terminal run is never earlier than the true terminal time, so a repaired deadline falls at or after the real one — retained longer than required, never purged early. It is opt-in, idempotent, and compare-and-set against the revision it read, so a raced record reports `conflicted` instead of being clobbered. **Run it once the fleet is fully on version-2 binaries, not during the rolling update:** a repaired record carries version 2, which a version-1 peer fails closed on. A migration is complete when a pass over the same scopes reports `conflicted: 0` and `stamped: 0`.
- The stored MCP descriptor set (`McpDescriptorSet`) is at schema version **2** (issue #85 ask 3). A build before version 2 refuses a version-2 set, so a deployment upgrades every reader of its stored sets before it publishes from a build that writes version 2; a version-1 set keeps decoding. A set a deployment assembles in code from stored descriptors carries the lowest schema version among its sources: stamped version 2 while it holds a version-1 descriptor, it fails the output-schema check at executor construction.
- The durable graph run state (`CURRENT_AGENT_GRAPH_STATE_SCHEMA_VERSION`, inline in `AgentRunState.graph_state`) is at schema version **2** (issue #110). Version 2 carries the wait reason `AgentGraphWaitReason::Reconciliation` (a node parked on a person because its effect may have run), `AgentGraphNodeState.effect_generation` (serde-defaulted, zero for every node that exists today), and effect ids and dedupe keys suffixed `;gen={g}` from generation one. `AgentGraphScheduler::initialize_state` stamps 2 on every new graph; a graph state created at 1 keeps saying 1 until its first park or resume, which raises it to 2 at that write, and both generations round-trip a version-1 state. Every reader that validates a graph state — the scheduler's and the bridge's plan-state validation, and `AgentStepRunner::update_graph_state` before it persists — refuses a state whose version is newer than its own with `graph-state-schema-unsupported` (the runner answers `workflow-mismatch` on the field `graph_schema_version`). The gate runs on a decoded state, so it answers a typed error for a newer version whose added values are serde-defaulted fields; a newer version that adds an exhaustive-enum variant still fails at decode before any gate runs, as this bump's wait reason does in a version-1 binary. That gate does nothing for this bump's older binaries, which have none; it is what the next additive bump relies on.
- **What version 2 writes, and who writes it.** `AgentGraphWaitReason::Reconciliation` (in `AgentRunState.graph_state` node states) is written only by `EffectFailed` with disposition `reconcile`; `AgentCommandKind::GraphReconciliationDecided` (in durable inbox entries) only by the decision command; `effect_generation` only by the `not-executed` decision's resume (absent means 0); the `;gen={g}` effect ids and dedupe keys (outbox entries and `scheduled_effect_ids`) only by the first schedule after a re-offer; the target attribute `agent_effect_max_attempts` by a plan that declares it or a request that sets it. Only the first is a value an older binary cannot decode: the wait reason is an exhaustive enum inline in the run state. The command kind is stored as an opaque payload that loading never decodes, so it fails only a consumer that decodes stored inbox payloads itself; the other three are additive. Neither the wait reason nor the command kind is written by any automatic path — no timer, recovery, retry or scheduler pass produces them — so a fleet that only reads version-2 binaries holds no version-2 value until a caller sends one. **Roll out in two steps:** first move every replica to a binary that reads version 2 while sending no `reconcile` disposition and no decision (a version-1 replica that still exists decodes every record); then, once every replica reads version 2, start sending them.
- The decision event (`AgentDecisionEvent`) is at schema version **2** (issue #119). The stamp is the version of the `AgentDecisionEventVocabulary` that wrote the event, not of its kind. `Version1`, the default, writes only the ten kinds a binary at the earlier pin (`bc0c224`) decodes and stamps every event 1. `Version2` adds the kinds `request-reconciliation`, `resolve-checkpoint`, `escalate-checkpoint`, `cancel`, `handoff` and `supersede`, and stamps every event 2. The four optional fields (`checkpoint`, `effect`, `outcome`, `run_status`) are written only under `Version2`, like the six kinds. A version-1 reader ignores them on decode, but a binary at the earlier pin that re-persists a run record writes the events it still owes back without them, and flushes them again; a sink that checks a resend's content against what it holds would answer that resend as a conflict. Under `Version1`, a binary at the earlier pin therefore reads and writes back every event unchanged. A new kind is a wire change for every strict reader: the older binary fails to decode it, on the stored event, on the run record whose outbox still owes it, and on the A2A coordination replay (`AgentCoordinationEventKind::Run`) for a client that decodes the kind strictly. **Roll out in two steps:** first move every process that loads the run store or reads the sink to a binary that reads version 2, with the vocabulary at `Version1`; then, once every one of them has moved, select `Version2`. A rollback to the earlier pin during step 1 is inside the window, subject to the run record bound below. **Rolling back past the new pin after `Version2` is outside the compatibility window:** a binary at the earlier pin cannot load a run record that still owes a version-2 event, and cannot decode version-2 events the sink already holds until they age out of retention (`AGENT_DECISION_EVENT_RETENTION` is 256 per run in the reference sink). Selecting `Version1` again stops new version-2 events but undoes neither. **The next bump:** the reader window must reach back to the oldest vocabulary a deployment can still select, so a bump to 3 either retires `Version1` or widens the window. **Run record bound:** the same change raised `AGENT_RUN_STATE_GROWTH_RESERVE_BYTES` from 96 KiB to 128 KiB and `AGENT_RUN_MATERIALIZED_MAX_BYTES` from 176 KiB to 208 KiB, so a replica at the earlier pin still enforces 176 KiB in its transitions. During rollout step 1 (or after a step-1 rollback), a run record a new replica grew into the 176-208 KiB range (a large working set plus a backed-up outbox while the sink is down) is refused transitions on an old replica until it reaches a new one or its outbox drains.

- The context snapshot (`MemoryContextSnapshot`) is at schema version **2** (issue #69). The stamp is staged by content, not by build: a snapshot is written as version 2 exactly when a communal search ran for its turn, and as version 1 otherwise. A version 1 snapshot from this build has the bytes and the digest it had before, and a binary at the earlier pin (`86cf087`) reads it. Version 2 changes `communal_claims` from a list of ids no writer ever filled to the selected claims themselves, and adds `communal`, the record of the search. Its digest covers that record. On load, in the snapshot's own decoding and so on every store, a version 1 snapshot that selects a claim or records a search is refused, and so is a version 2 snapshot that records none. **A binary at the earlier pin and a version 2 snapshot:** with a selected claim it fails to decode the snapshot, so it can never read a claim as something else; with none selected, the PostgreSQL snapshot store refuses version 2, while another store decodes the record and drops the search it does not know (the model input is the same, because no claim was selected). **Upgrade every process that reads context snapshots before any run is wired with a communal bundle.** No run writes version 2 until one is.

- An ended run's ambiguous memory promotion or claim append is now answerable (issue #120). Behaviour change: where a possibly-executed attempt whose recovery retry the authority refused used to park `Indeterminate` with no checkpoint, both resolution paths refused an ended run, and the settle pass's repair skipped one, the park now opens a reconciliation checkpoint (decisions `confirmed-completed`, `confirmed-not-executed`, `escalate`, `abandon-and-fail`; no `compensate`), `ResolveCheckpoint` and `ResolveIndeterminateEffect` answer it at any time after the run ended, a timer escalates it, and the settle pass repairs a park that has none. A reconciliation checkpoint opened while the run was live keeps `compensate` on its durable record after the run ends, and the point query stops listing it there; a `Compensate` decision on an ended run is refused `run-terminal`. On an ended run a `ConfirmedExecuted` must carry the effect's own receipt, a `Failed` or an `Exhausted`; any other outcome is refused `effect-policy-invalid` and changes nothing. An approval a tool-calling turn opened for a gated promotion or claim append, left open when the run ended, is now answered and timed as on a live run: a grant dispatches the effect, a denial fails the generation, and a timer expires it and fails the generation, without moving the run's status; `bc0c224` left it waiting. The scope is exactly `AgentRunEffectKind::outside_the_turn()`; a compensation or workflow cancel parked on an ended run is unchanged (issue #123), and every other resolution on an ended run is still refused `run-terminal`. The terminal status, reason and stamp never move, and no durable field, variant, type or error code is added. During a rolling update:

  | A `bc0c224` replica loads an ended run with the checkpoint open | It loads and its snapshot shows the checkpoint, listing `compensate` if the checkpoint was opened while the run was live. Its settle pass leaves the run alone. |

After it, a `bc0c224` binary refuses a resolve on an ended run `run-terminal` again, no longer escalates these checkpoints on timers or expires an approval left open on one of these effects, and opens no checkpoint for a new park. ## Kubernetes Rolling Updates

Recommended sequence:

1. Release N with a declared N/N+1 protocol window, additive schema policy, and manifest/API metadata.
2. Build release N+1 without removing fields, changing field meanings, or changing required defaults used by N.
3. Deploy N+1 through a Kubernetes rolling update with readiness gates enabled.
4. Let incompatible nodes fail readiness instead of joining the cluster or acquiring shards.
5. Drain and replace pods one at a time, respecting the PodDisruptionBudget.
6. After every pod is on N+1, the next release may advance the window to N+1/N+2.

The example manifest includes:

- `RAKKA_PROTOCOL_VERSION`
- `RAKKA_COMPAT_MIN`
- `RAKKA_COMPAT_MAX`
- `RAKKA_COMPAT_POLICY`
- `RAKKA_MANIFEST_VERSION`
- `RAKKA_GENERATED_API_VERSION`
- `rakka.rs/protocol-version`
- `rakka.rs/compatible-min`
- `rakka.rs/compatible-max`
- `rakka.rs/manifest-version`
- `rakka.rs/generated-api-version`

## Observability

Compatibility failures must be observable through multiple surfaces:

- Typed errors: incompatible discovery returns `ClusterError::IncompatibleNode`, wrapped as `ClusterShardingError::Cluster` at the sharding runtime boundary.
- Readiness: Kubernetes readiness includes `compatibility-not-accepted`.
- Metrics: `rakka.k8s.compatibility` records `state=accepted|rejected`, and `rakka.k8s.readiness` records `outcome=ready|not-ready`.
- Remote delivery: unsupported schemas fail through the serialization registry before delivery.

Agent-domain telemetry names are a compatibility surface of their own, because a deployment's dashboards, alerts, and Collector rules are written against them:

- Every `rakka.agent.*` metric name, its instrument kind, its unit, and its bounded label keys are enumerated in [`rakka-agent-observability-catalogue.md`](rakka-agent-observability-catalogue.md) and held as data in `AGENT_DOMAIN_METRIC_INSTRUMENTS`. Renaming a metric, changing its kind or unit, or adding a label key is a compatibility change; adding a new metric is not. A metric declared in the crate but missing from the catalogue fails `cargo test -p rakka-agent --test metric_catalogue`.
- Every bounded operation class of `AgentSegmentOperation` and the span name and kind it maps to under the `otel` feature are likewise enumerated there. The OpenTelemetry GenAI semantic-convention revision the mapping targets is pinned at `AGENT_GENAI_CONVENTION_REVISION` and stamped into every exported batch's instrumentation scope, so a consumer can tell which revision produced a record. Upgrading it is the specification 17.20 review, never a side effect, and never a durable-state migration.
- **Span** export records carry only the keys in `AGENT_SPAN_ATTRIBUTE_KEYS`. **Log** records carry a deliberate superset, `is_agent_log_attribute` = `AGENT_SPAN_ATTRIBUTE_KEYS` plus `AGENT_LOG_ATTRIBUTE_KEYS` — the substrate's durable correlation identities (`rakka.agent.run_id`, `tenant_id`, `correlation_id`, `causation_id`, `audit_event_id`, and the rest), because specification 17.13 asks a structured log to carry exactly the identities 17.12 forbids on a *metric*, and applying the span list to logs would strip the audit trail while claiming to redact it. A key outside the applicable list is dropped before export rather than renamed, so a consumer may rely on the absence of prompt, completion, tool-payload, memory-content, and credential keys from **both** — not merely on a Collector rule removing them. A log record's `resource` is not an attribute set and is not filtered by either list: it is the emitting service's identity (`service.name` and its siblings), bounded but not allowlisted.
- The stable `error.type` values a failed span carries are a compatibility surface, because 17.6 makes the key a grouping attribute and 17.16 asks a retention policy to select on it. The agent domain writes the seven in `rakka_agent::AGENT_SEGMENT_ERROR_TYPES` — `rakka.agent.authority`, `rakka.agent.dispatch`, `rakka.agent.effect`, `rakka.agent.model`, `rakka.agent.outbox`, `rakka.agent.recovery`, `rakka.agent.tool` — and the A2A edge writes one more of its own, `rakka.a2a.ingress` (`rakka_a2a::agents::A2A_INGRESS_ERROR_TYPE`), because the protocol adapter owns the ingress span the agent domain defers to it. The list is data rather than prose, and `cargo test -p rakka-agent --test metric_catalogue` holds it to the call sites in both directions. The accompanying `rakka.error.code` is the subsystem's own stable code, bounded at `AGENT_SEGMENT_ERROR_CODE_MAX_LENGTH`; a new code is not a compatibility change, a new `error.type` is.
- `gen_ai.request.model` carries the deployment's bounded **model profile** — the name it configured and the run pinned — never a provider's internal model string, which Rakka does not see. `gen_ai.agent.version` carries the **agent definition revision** and nothing else; it briefly carried the model profile as well, which made one dimension hold two unrelated vocabularies. A deployment that configures no profile gets neither the attribute nor a model in the span name: the chat span is named `chat` rather than `chat ` with a trailing space, which is a different span class to every backend.
- The `signal` label on `rakka.agent.telemetry.flush.failures` and the three `rakka.agent.telemetry.export.*` instruments takes its values from two closed vocabularies. `rakka_agent::AGENT_TELEMETRY_SIGNALS` holds what the crate writes (`decision-events`, `spans`); the application boundary's OTLP exporter declares its own (`otlp-traces`, `otlp-metrics`, `otlp-logs`), because the SDK and the exporter live in the deploying binary under specification 17.17. Each is held to a bijection against its own call sites — `cargo test -p rakka-agent --test metric_catalogue` and `cargo test -p rakka-example-agent-otlp-export-acceptance --test exporter_failure` — so a value neither list names cannot be written, and a value nothing writes cannot sit in a list as a promise.
- The pinned OpenTelemetry SDK generation (`opentelemetry` 0.29) and the pinned Collector distribution (`otel/opentelemetry-collector-contrib:0.159.0`) are recorded, with their rationale and revalidation procedure, in [`rakka-agent-telemetry-validation-matrix.md`](rakka-agent-telemetry-validation-matrix.md). Neither appears in a published crate's dependency graph: both belong to the `publish = false` example that owns the application boundary.

- Issue #68 ("knowledge-graph retention, tombstone and deletion") adds two required methods to `KnowledgeGraphStore`, four stable refusal codes, one optional field on the claim record, and a change to the PostgreSQL graph schema. **Source-breaking for an outside implementor.** `KnowledgeGraphStore::tombstone` and `KnowledgeGraphStore::delete` have no default body and no capability flag, because specification 13.1 makes them mandatory for every memory API. A store implemented outside this repository does not compile until it has both. The three implementations in this repository have them. **The four codes.** `claim-tombstoned`: the claim is a tombstoned stub, so it cannot transition, be tombstoned again, or be appended. `claim-operation-erased`: the replayed operation's payload was erased by a later tombstone or delete of its claim. `claim-tombstone-content`: a record marked tombstoned still carries a statement, evidence, or an embedding. `claim-delete-stale`: the claim is no longer in the state a delete expected. No existing code changes meaning. `claim-operation-conflict` gains one cause in the same sense it always had: a tombstone's or delete's operation id sent again for a different claim. An erasure operation id belongs to one claim. The claim-append executor treats all four as definitive refusals, so a retried append of an erased claim fails its effect once and does not end the run. **The claim record is at schema version 2, staged.** Version 2 carries `tombstone`, an optional field that is absent from a live claim's encoding. A claim is written at version 2 only when it is a tombstoned stub; a live claim is still written at version 1 and encodes to the same bytes as before (`CLAIM_LIVE_SCHEMA_VERSION`). It never reads a stub's markers as a statement. **A consequence for the next bump.** Because live claims stay at version 1, a bump to version 3 would put every live claim outside the default N/N+1 window.   | A claim whose lease had lapsed before the pass reached it was started anyway | It is not started. It is counted in `AgentDispatchPass::lapsed`, nothing is written for it, and any worker can claim it |
  | A pass that met an error returned it and left the claims it had not started `Claimed` until the batch's lease lapsed. They counted against their class's concurrency limit meanwhile | The pass first gives those claims back: one fenced write sets each to `Pending` with no lease, claimable at once under the next fencing token. The claim that failed keeps its lease. The error returned is the one the pass had |
  | `AgentDispatchPass` did not carry the tickets a claim left at a concurrency limit | `AgentDispatchPass::concurrency_limited` carries the count the fleet's claim already made. That count stops once the batch is full, so zero is not evidence that no limit binds |
  | `AgentDispatcherWorker::run_once` had the first and the third gap | It renews and releases in the same way. `dispatch_claim` is unchanged, and a claim that is no longer current still ends the cycle with `claim-fenced` |

  **The fence.** A renewal and a release each apply only to a claim that is still current in the record the write is applied to: the same worker, the same fencing token, a lease still active. A claim that lapsed, was taken over, finished or was pruned is left as it is. A renewal also leaves an entry whose run's cancellation was requested, and never shortens a lease. A release keeps the entry's last fencing token, so a late write under the released claim is answered `claim-fenced`; it keeps a cancellation request too, and such an entry is finished by the cancellation instead of claimed. Both read the record again when they lose their compare-and-set, as a settle does, and a release reads it before its first write too.

  **A hold is spent by the settle that lands.** `hold_claims` names the claims the next settle renews, and a settle that is written leaves nothing held. A worker names what it still holds before each claim it runs; a claim nobody names again is leased for at most one more lease. Both loops hold nothing once a batch has ended short. The `AgentDispatchClaim` value a worker holds keeps the `lease_expires_at` of its claim pass, which can be earlier than the entry's lease after a renewal and never later.

  **What is not renewed.** The claim being run. A call that outlives the lease loses its claim as before, its settle is answered `claim-fenced`, and the claims the pass held behind it lapse with it. Nothing renews during a call. **What a renewal costs.** A renewed batch stays with its worker: a ticket claimed behind long calls waits for every one of them, where one lease used to bound that wait and let another worker take it. The batch size bounds it now.

  **What is not released.** The claim that failed, whose lease is its backoff and can be a full lease counted from the settle before the failure, where it used to be what was left of the batch's; the claims of a worker that was killed, or of a pass whose future was dropped; and anything at all when the release's own write fails, which is logged and does not replace the pass's or the cycle's error.

  **What an earlier binary reads.** A renewed entry is a claimed entry with a later `lease_expires_at`. A released entry is `Pending` with `lease: null` and a `last_fencing_token` above zero, which is what a registration has always written for a claim whose lease lapsed: `a_released_entry_is_the_entry_a_registration_makes_of_a_lapsed_claim` builds the two side by side, and `a_record_whose_one_claim_was_released_keeps_these_bytes` holds the bytes. A worker at `ff9a495` or `c4be3d9` beside a newer one leaves a renewed lease alone and claims a released entry. Its own batches are neither renewed nor released, and at `ff9a495` its settle does not read again.

  **Public names.** `AgentDispatcherFleet::hold_claims` and `AgentDispatcherFleet::release_claims` in `rakka-agent-workflow`; `AgentDispatchPass::lapsed` and `AgentDispatchPass::concurrency_limited` in `rakka-agent`. The two fields are source-breaking only for a struct literal or a pattern that names every field of `AgentDispatchPass`. **New stable strings**, on the counter `rakka.agent_workflow.dispatcher.fleet`: `operation=renew, outcome=renewed` and `operation=release, outcome=released`, each with `detail=none` and each counting entries.

  **The concurrency limit.** An entry counts against its class and its target from its claim until it is settled or its lease lapses. The settle is what tells the record a call has ended, so a call that ended and whose settle was lost for good holds its slot for the rest of one lease; that takes four lost writes running, or a worker lost between the delivery and the settle. A batch's claimed and unstarted tickets hold slots too, and a failed pass now gives those back.

- Issues #159 and #160 ("a registration or a claim that loses its compare-and-set on the fleet record still fails the dispatch pass", "nothing counts a fleet settle's re-applications, and its tries run back to back") change what follows a lost write to the dispatcher fleet record. **No durable field, status, schema version or error code is added**, and a rollback is clean.

  | Before | Now |
  |---|---|
  | A claim that lost its compare-and-set returned `revision-conflict`, and the pass failed | The fleet reads the record again and claims again, up to three more times. Each attempt is made whole from the record it read: what is due, the limits, the batch and the fencing tokens. A lost attempt's claims are dropped; its write did not land, so it leased nothing |
  | A registration that lost its compare-and-set returned `revision-conflict`, and the pass failed | Its caller reads the fleet record again, then the run's due list again, and registers again, up to three more times. `AgentRunEffectDispatcher` and `AgentDispatcherWorker::refresh_run` do this. `AgentDispatcherFleet::register_due_effects` itself is still one try |
  | `AgentDispatchPass::registered` and `AgentDispatcherRegistration::registered_effects` were the one try's count | They are the count of the try that landed: what that write changed. An effect another worker registered in between counts for nothing |
  | Nothing counted a lost write | Each lost compare-and-set of a registration, a claim, a settle, a release and a prune is counted once on `rakka.agent_workflow.dispatcher.fleet` |
  | Re-applications ran back to back | A re-application waits a random time first: between 5 and 10 ms before the first, 10 and 20 ms before the second, 20 and 40 ms before the third, under 70 ms in all. A settle's first re-application still follows at once, so a settle asks for under 60 ms |

  **Why the registration is not re-applied inside the fleet.** A registration is handed a list of a run's due effects, and its lost write is a fence (issue #145): the list must be no older than the record it is written against, or it can name an effect another worker has since run, finished and had pruned. Re-applying the same list to a newer record would put that effect back. So the list is read again too, after the record, and only the caller can do that.

  **The wait.** It is never on the fleet's clock, so a fleet handed a logical clock that moves only when it is told to still waits and goes on. By default a thread sleeps for the time asked and wakes the task (`AgentFleetWritePause::Thread`): no async runtime and no timer is needed, and no dependency is added. An application replaces it with `AgentRunEffectDispatcher::with_fleet_write_pause` or `AgentDispatcherFleet::set_write_pause`, to wait on its runtime's timer or in a simulated time, or, with a wait that ends at once, not to wait. The times above are what the fleet asks for; how long a wait really takes is the waiter's. A wait separates writers that lost to the same write. It does not shorten the time between a read and its write, which is where a write is lost.

  **Why a settle's first re-application does not wait.** A settle is written from the copy its claim left, which is as old as the call it settles, so its first loss says the copy was old. Every other write follows a read, so its first loss is already a write that landed between a read and the write after it.

  **What an earlier binary does in the same fleet.** It reads nothing new: the record's bytes are what they were. Its own registrations and claims fail their pass on a lost write as before, and it counts and waits for nothing.

  **What gets busier.** A registration or a claim that lost used to leave the record alone until its next pass. It now reads the whole record and tries again within tens of milliseconds. The writes that land are the ones that would have landed a pass later, so they land sooner and closer together, and there are more reads and more attempts. A settle that waits does so while its claim's lease runs: a lease that had under 60 ms left can lapse in the wait, and the settle is then answered `claim-fenced`. This is not measured under load. `operation=settle, outcome=revision-conflict` is the count to watch across the change.

  **Public names**, all in `rakka-agent-workflow` but the last: `AgentDispatcherFleet::registration_lost(reapplied, error)`; `AgentFleetWritePause` (`Thread`, `With`, and the constructor `with`) and `AgentFleetPauseFuture`; `AgentDispatcherFleet::with_write_pause` and `set_write_pause`; and `AgentRunEffectDispatcher::with_fleet_write_pause` in `rakka-agent`. No signature changes.

  **New stable strings**, all on the counter `rakka.agent_workflow.dispatcher.fleet`: `operation=settle`, which the fleet did not record before; `outcome=reapplied` with `detail` `1`, `2` or `3`, the number of the re-application the loss led to; and `outcome=revision-conflict` with `detail=none`, a loss returned under that code. Both outcomes are recorded under `operation` `register`, `claim`, `settle`, `release` and `prune`. No label carries a run, effect, tenant or worker id. A registration made through `register_due_effects` alone is counted only when its caller asks `registration_lost`.

  **What a settle that ran out leaves** is not changed, and is now counted. The ticket's outbox row is finished and its fleet entry stays `Claimed` until its lease lapses. After a delivered result, the re-claim invokes nothing and ends the entry `Cancelled`. After a call that spent its attempts, the run has not been told: the re-claim ends the entry `Exhausted` and tells it then. After a failure with attempts left, the re-claim is the next attempt.

  **Not changed.** The bound of three re-applications. The two writes of a cancellation through `AgentDispatcherWorker` (`request_run_cancellation`, `finalize_run_cancellations`): one try each, not counted.

No type, field, status, code, event or schema version is added, and an ended run is not affected: its status never moves.

  | Answer to the park | Before | Now |
  |---|---|---|
  | `ConfirmedExecuted` with a successful outcome, or `ConfirmedCompleted` at the checkpoint | The run stayed `WaitingForReconciliation` unless the outcome itself rested the turn. A memory promotion's, a claim append's and a goal evaluation's never did, and a tool call's did not while another effect of its turn was out | The run takes the status of what it rests on |

  | `ConfirmedNotExecuted` | The dispatch wait (`WaitingForEffect`, or the wait of an open gate), whatever the run rested on | The status of what the run rests on. For a call whose outcome moves the run that is still the dispatch wait |
  | `Compensate` | The run winds down behind the compensation | Unchanged |
  | `Escalate` | The park stands | Unchanged |

  **The status of what a run rests on** is the dispatch wait while a call whose outcome moves the run is outstanding, and `Running` otherwise. Those calls are the model call, a tool call, an A2A send and a workflow start. The dispatch wait is `WaitingForEffect`, or `WaitingForApproval` or `WaitingForAuthorization` while a gate on one of those calls is open. A memory promotion, a claim append, a goal evaluation and a workflow cancel are committed without a status, and the success of one neither puts the run on a status nor takes it off one, so neither they nor their gates are part of it. The status is read when the park ends, and not kept from before the park: a tool result that lands during the park rests the turn, and the run goes on from there.

  **What this changes for a reader of the status.** A live run that was parked on a memory promotion, a claim append or a goal evaluation no longer reports `WaitingForReconciliation` after the answer, and no longer reports `WaitingForEffect` after a re-send while it rests on its proposal or its children. `WaitingForReconciliation` does not permit progress, so before this a run answered that way took no loop transition until something else wrote its status, and a run with nothing in flight never did.

  **A record an earlier binary left parked** with nothing to reconcile is repaired by the first settle pass that touches it, in one write. `Settle` runs one, and so does any command or exchange the run applies, a checkpoint timer with nothing due among them. A read, a refused command and a fan-in deadline with nothing due do not, so a run with nothing in flight stays as it is until a settle reaches it. A park that still has its ambiguous outcome is not written. A record a re-send left on `WaitingForEffect` is not repaired: that status permits progress, and the next status write corrects it.

  **Two differences on the re-send.** With the gate of a goal evaluation open, re-sending a call that moves the run used to put the run on that gate's wait, `WaitingForApproval` or `WaitingForAuthorization`. It now puts it on `WaitingForEffect`: the run takes the status of what it rests on, and that is not read from an evaluation's gate. And re-sending a goal evaluation or a workflow cancel used to put the run on the dispatch wait; it now leaves the run on what it rests on, as it does for a memory promotion and a claim append.

  **Not changed.** A turn that commits while a goal evaluation or a workflow cancel is outstanding is still rested on a wait that counts it, and on the approval wait of an evaluation's gate; and a granted evaluation gate still writes the dispatch wait (issue #166, below, has since narrowed that grant to a run that is on a dispatch wait). Those are the turn's own rules and this entry does not touch them; only the status an answered park leaves is read without them. A workflow cancel that fails still winds its run down. The park itself, the checkpoint and its decisions, and what each answer does to the effect are as they were.

  **The rule.** A live run that is not parked and not winding down, and that is on `WaitingForApproval` with no approval of the turn waiting, or on `WaitingForAuthorization` with no security authorization of the turn waiting, has its status recomputed.   **Not changed.** What a turn waits for: a turn that makes a call and commits with a goal evaluation or a workflow cancel outstanding is still held for it, and is rested by the settle pass once it ends.
