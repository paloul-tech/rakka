# Changelog

All notable Rakka changes should be recorded here before a release candidate is cut.

The format follows Keep a Changelog style sections, and versioning is expected to follow SemVer once v1 release candidates begin.

## Unreleased

### Added

- `scripts/validate.sh` as the required local validation entry point.
- `scripts/package-check.sh` as the offline package metadata and publishability check entry point.
- V1 release-candidate review docs for reliability boundaries, N/N+1 rolling updates, known limitations, post-v1 roadmap, and final review checklist.
- Phase 5 agent workflow autonomy APIs: effect target catalog and policy validation, A2A peer adapter contracts, dispatcher registry routing, A2A peer/webhook/push dispatch classes, and deterministic dispatcher cancellation marking.
- `rakka-agent`: the crate that will own the durable agent domain — goal, typed task, run, evaluation, handoff, delegation, team, moderation, and workflow-tool contracts, the durable loop runtime, the provider-neutral model adapter trait, the continuous wake controller, the escrow budget ledger, autonomy admission, guardrails, checkpoints, tool authority, memory traits, structured telemetry, bounded operational queries, and deterministic test support. The first release landed the crate scaffolding: the documented module map, the `rig` (default) and `otel` feature gates, and the `agent`, `agent-rig`, and `agent-otel` facade features. The crate builds and tests with `--no-default-features`, which `scripts/validate.sh` now enforces.
- `rakka-agent` identity, definition, and agent-entity contracts:
  - Tenant-scoped identities (`AgentId`, `AgentGoalId`, `AgentTaskId`, `AgentRunId`, `AgentDelegationId`, `AgentWakeId`, `AgentEnvironmentRef`, `KnowledgeSpaceId`) that stay distinct types even where their values coincide, plus the composite scope keys (`AgentScope`, `AgentTaskScope`, `AgentRunScope`) that address the sharded entities. Identifier values are validated and fail closed on deserialization so that flattening a composite scope into an entity or persistence id stays injective and cannot alias two tenants onto one durable record. `AgentRunBinding` fixes a run's task at construction; there is no setter to re-target it.
  - `AgentOperationId` and `AgentOperationKind`: derived — not generated — stable operation and deduplication identifiers, convertible to the substrate's `AgentDeduplicationKey` and `AgentCommandId` so the durable inbox and outbox deduplicate on the same value the agent domain reasons about.
  - `AgentDefinitionRevision`, `SettingsRevision` with the turn-bound / immediate-safety / run-pinned timing classes, and `AgentSetupRevision`. `AgentAuthorityEnvelope` carries the definition's authority in one place, and a setup or settings revision may only narrow it: introducing an undeclared tool, weakening a mandatory guardrail, choosing an unapproved model, widening credential/knowledge/environment access, adding an unauthorized peer, downgrading a tool's effect safety, rerouting a tool through a different execution policy (opaque policies cannot be ranked, so the declared routing is pinned), or raising a budget ceiling is rejected with a stable reason code. Definition content is validated at construction, on deserialization, and again at the entity's accept path, so an out-of-bounds description can neither cross the wire nor be persisted, and a settings revision's change list is bounded on the load path as well. `effective_settings_for_turn` resolves a run's pinned revision against the agent's current one.
  - Sharded `AgentEntity`, keyed `(TenantId, AgentId)`, owning the durable definition, lifecycle status (`Active`/`Suspended`/`Terminated`), current settings revision, policy and logical credential-binding references, and the agent-private memory namespace. Its `AgentEntityCommand`/`AgentEntityReply` protocol is serializable from the first commit and routable over `rakka-remote` via `init_agent_entity_remote_sharding`. Administrative commands deduplicate on their operation id and return the original outcome on replay; settings updates are fenced on the settings revision they expect to succeed, and suspend/resume/terminate on the monotonic lifecycle revision they expect to advance, so a replay that has aged out of the deduplication window cannot reorder over a decision its initiator never saw. Instantiation takes the definition content and publishes the initial revision itself, so a foreign revision number or schema version cannot enter the first durable record. `load_agent_entity_state` is the durable read path that keeps run creation out of the entity's mailbox.
  - Schema versions on every persisted record, with a default N/N+1 compatibility policy (`AgentSchemaPolicy`). A record written by a newer binary, or one older than the supported window, fails closed on load rather than being interpreted with guessed semantics.
  - No resolved credential material appears in durable state, snapshots, or replies; credential bindings are logical references only.
- `rakka-agent` inter-entity choreography substrate:
  - `AgentExchangeJournal`, the durable saga record every choreography participant embeds in its own state. It is the entity's outbox and inbox at once: the exchanges it owes, the operations it has settled, and the operations it has applied together with the logical result each returned. Because it lives inside the participant's state record, an exchange is persisted in the *same* compare-and-set as the domain transition that owed it, and a receiver's decision is persisted in the same compare-and-set as the transition that produced it — so there is no window in which an entity has transitioned but forgotten what it owes, and none in which it has decided but not recorded the decision.
  - `AgentExchangeHost`, the durable host that owns recovery, the fail-closed schema check, deduplication, and the compare-and-set write of every transition. Participants supply only bounded in-memory transitions through `AgentExchangeParticipant`, and an accepted exchange may owe the next one atomically, which is what makes the canonical creation → assignment → run-acceptance chain of specification 9.8 unbreakable. A participant transition is stamped with the commit-time clock the host passes it, never with the envelope's initiator-side creation time, so a receiver's durable timestamps cannot regress under a skewed or replayed initiator. `drive_pending_exchanges` re-drives everything an entity owes from durable state under the operation ids its transitions first minted, so calling it after a transition, after recovery, or on a timer are the same operation.
  - `AgentEntityAddress` (agent, task, and run classes) as the routing key and durable record locator of an exchange, `AgentExchangeKind` for the six exchanges of M1 (creation, assignment, result proposal, budget allocation, settlement, and return), and the bounded, typed `AgentExchangePayload`. An exchange may not cross a tenant boundary, an entity may not apply an exchange addressed to another, and one operation id may not name two exchanges.
  - `AgentExchangeTransport`, `ShardedExchangeRoute`, `AgentExchangeRouter`, and `register_agent_exchange_codecs`: an exchange resolves its target's shard owner and is then either asked of the local entity or asked of the owning node over `rakka-remote`. Both paths reach the same durable accept path, so colocation changes the transport and never the durable record — and an exchange stays correct after its entities move to different nodes. Delivery stays at-most-once; a delivery failure is never read as evidence that the receiver did not apply the exchange.
  - The per-exchange failure-window table (initiator loss before send, receiver loss after acceptance, reply loss, duplicate delivery) is a doc section of `rakka_agent::choreography`, with the test that proves each row.
  - `rakka_agent::testkit` gained `ChoreographyProbe`, a fenced reference participant, and `InProcessExchangeTransport`, which injects those failure windows.
- `rakka-agent` typed-task entity:
  - Sharded `AgentTaskEntity`, keyed `(TenantId, AgentTaskId)`, owning the public work lifecycle (`Created`/`Blocked`/`Assigned`/`InProgress`/`WaitingForInput`/`Completed`/`Failed`/`Cancelled`) independently of any one execution. Its `AgentTaskEntityCommand`/`AgentTaskEntityReply` protocol is serializable from the first commit, and `init_agent_task_entity_remote_sharding` makes the entity reachable over `rakka-remote`, where the exchange envelope is the cross-entity command surface. Commands deduplicate on their operation id and return the original outcome on replay; the entity is a choreography participant, so an exchange it owes is persisted in the same compare-and-set as the transition that owed it.
  - Versioned `AgentTaskDefinition` with input/result schema references, deterministic result rules, rejection and assignment limits, dependency-failure policy, per-task budget ceilings, ownership policy, and required skills. It is validated at construction, on deserialization, and again at the entity's creation path; rule content is itself bounded (`AGENT_TASK_RULE_POINTER_MAX_LENGTH`, `AGENT_TASK_RULE_ONE_OF_MAX_VALUES`, `AGENT_TASK_RULE_VALUE_MAX_LENGTH`), so a definition cannot grow the materialized record without limit. `TypedTask<I, R>` is the only place generics appear: it binds Rust types to the definition's schema references as compile-time ergonomics, while durable state and exchange payloads stay non-generic, bounded, and versioned. Decoding an accepted result under a mismatched definition or schema revision fails closed.
  - The creation → assignment → run-acceptance flow of specification 9.8. The assignment decision reads the agent's durable definition and admission state through `load_agent_entity_state` — never a synchronous round trip through `AgentEntity`, so a popular agent is not a bottleneck for its own runs — and then commits the decision, the assignment generation, and the run-creation command it owes in one transition. The run identity is *derived* from the task and the generation (`run_id_for_assignment`), so replaying an assignment resolves to the same run rather than creating a second one. An agent that is suspended, absent, or does not declare the task definition in its authority envelope is refused, and the task stays assignable rather than failing; an unchanged refusal is recorded in history exactly once, however often the task settles. Because every run id must remain a valid identity for every reachable generation, an agent-owned task id longer than `AGENT_TASK_ASSIGNABLE_ID_MAX_LENGTH` is refused at creation (`task-id-too-long`) rather than discovered at decision time. A delegated creation's accepted reply carries its `AgentTaskOutcome` under `AGENT_TASK_CREATION_OUTCOME_PAYLOAD_TYPE`, so `AGENT_TASK_DECISION_PAYLOAD_TYPE` names exactly one wire shape.
  - Deterministic in-entity result validation. A proposal is fenced on the current assignment generation, checked against the definition and schema revision it claims, and then run through every `AgentTaskResultRule`; a rejection is a durable decision carrying the rule, its revision, the proposal's digest, the rejection count, and its causation, and it is returned unchanged on replay. Exhausting the rejection budget fails the task; it never silently accepts the result it just refused. A superseded run's proposal consumes none of the live run's budget. Model-assisted evaluation stays a durable effect, never I/O inside a transition.
  - Bounded materialized state (specification 9.6): the record holds the current identity, status, revisions, dependency summary, assignment, pending references, accepted result, and terminal reason, and nothing that accumulates. Superseded assignments, proposals, and rejection decisions become `AgentTaskHistoryEntry` rows in an `AgentTaskHistoryStore`, readable only through a bounded, tenant-scoped cursor; content beyond the inline bound must arrive as an artifact reference. Admission reserves `AGENT_TASK_STATE_GROWTH_RESERVE_BYTES` of growth headroom below the materialized limit — the same reservation the id bound makes for derived run ids — so a task the entity admits is never later refused its own assignment, rejection, or terminal reason for want of room; a creation or late dependency declaration that would spend the reserve is refused instead, and a proposal whose causation id exceeds the identity bound is refused without a validation decision (`proposal-causation-too-long`). All durable task timestamps are stamped by the owner at commit time, never by the initiator's clock. History is written through a bounded outbox in the entity's own state and flushed idempotently, so no transition can commit while forgetting the history it owes.
  - Durable, bounded, acyclic dependencies. An edge is rejected if it would close a cycle against the dependency's own declared ancestry, and the default failed-dependency policy cancels dependents; `ContinueWithEvidence` must be chosen explicitly. Duplicate declarations inside one creation follow the post-creation rule: a repeat is idempotent, a conflicting policy is refused rather than last-wins, and the dependency limit counts edges, not declarations.
  - `rakka_agent::testkit` gained `RunAcceptanceProbe`, a minimal run that holds the far side of the assignment exchange still, and `InProcessTaskEntityTransport`, which drives exchanges into a real task entity that is re-materialized from durable state on every delivery.
- `rakka-agent` run entity and durable loop:
  - Sharded `AgentRunEntity`, keyed `(TenantId, AgentId, AgentRunId)`, owning one agent's contribution to one task: its loop state and status, its effects and accepted result, its own budget ledger, and its participation in the result-proposal exchange. `AgentRunBinding` fixes the task at construction, so a run serves exactly one task and one assignment generation for its whole life; handoff and reassignment create a new run. The `AgentRunEntityCommand`/`AgentRunEntityReply` protocol is serializable from the first commit, and `init_agent_run_entity_remote_sharding` makes the entity reachable over `rakka-remote`, where the exchange envelope is the cross-entity command surface.
  - The full run status set of specification 9.3. The substrate's single `WaitingForHuman` is split at this first commit into `WaitingForApproval`, `WaitingForAuthorization`, and `WaitingForReconciliation` — they resolve through three different durable decisions, and answering one is not answering another — so no agent-domain record was ever written under an unsplit status and no migration is owed. `AgentRunStatus::is_waiting_for_human` names the set the substrate's variant corresponds to, and is what slice 1.12 projects onto A2A. `Accepted`, `Running`, and `Cancelling` are not residency claims: the entity passivates whenever no bounded transition is immediately executable.
  - `AgentLoopPhase` and the versioned durable `AgentLoopState`: goal, task, turn, phase, the pinned agent definition and settings revisions, the context-snapshot reference a model effect was prepared against, pending effect references, the accepted result, sanitized rejection feedback, remaining budgets, pending checkpoint/timer references, and both the loop-state schema version and the adapter version — which version separately, so an adapter upgrade is an explicit migration rather than a silent reinterpretation of the turns the previous adapter wrote.
  - The execution rule of specification 9.5, enforced rather than asserted. Every loop arrow is one bounded transition and one compare-and-set, and every rest position is a durable wait: `PreparingContext` persists the model effect *and* the wait together, so there is no instant at which a run waits for an effect that was never recorded. `AgentRunEntityStore::settle_side_effects` cranks the loop from durable state alone — advance, dispatch, drive — so calling it after a transition, after recovery, or from a sweep are the same operation; `AGENT_RUN_MAX_LOOP_STEPS_PER_PASS` and `AGENT_RUN_MAX_SETTLE_ROUNDS` fence the handler's work.
  - The result proposal/decision exchange. The run persists its proposal before the exchange that carries it, under an id derived from the run and the turn, and it never makes the public task terminal by mutating its own state: the task's persisted validation decision is the source of truth for the outcome, and the run's state is the source of truth only for the run's consequence of it. A rejection returns sanitized feedback and a remaining-iteration count, and the run takes another bounded turn; an exhausted rejection budget fails the run rather than treating a refused result as accepted. A *refusal* — the task fenced the run by a newer generation, or has moved on — is not a validation decision, so the run stops rather than iterate, mapping the task's status onto `Superseded`, `Cancelled`, or `Failed`.
  - The interim durable effect: `AgentRunEffect` is a field of the run's own state, committed by the transition that decided it, and `AgentRunEffectSink` hands it to the existing agent-workflow `AgentEffect` outbox afterwards. The two cannot be one write, and that is the point — a run that committed `AwaitingModel` and then lost its node before writing the outbox row would wait forever for an effect nobody will dispatch. Dispatch is idempotent on the derived `effect_id`, so a re-driven flush names the same effect and shard movement cannot make one dispatchable twice. A result for an effect the run does not hold, or has already resolved, is refused by the run's own fence as well as by its deduplication log. Slice 1.7 retrofits the safety classes, the durable `Started` with its lease and fence, and the `Indeterminate` → reconciliation path onto this record.
  - `AgentModelTurn`: the Rakka-owned, versioned, bounded record of one model turn, and the only durable format for what a model produced — no provider type and no adapter's internal runner state ever reaches durable state. It carries assistant text, tool-call *requests* (a request, never an authorization: model output cannot widen what a run may do), an optional typed result proposal, and usage. It arrives the way every effect result arrives, as a durable command the dispatcher returns through the inbox, which is why the loop can be driven end to end before slice 1.6's adapter exists to produce one.
  - `AgentRunBudget`: the run's own durable ledger — remaining loop iterations, model calls, tool calls, tokens, cost, and deadline — allocated from the task definition's ceilings at acceptance and charged by the run's own single-entity transitions, never by reading a parent scope at dispatch time. A model effect is charged when it is persisted, not when its result returns, because an effect that reaches durable dispatch has been paid for whether or not its outcome is ever known. Exhaustion is a structured stop (`AgentBudgetExhaustion` carries the dimension, the limit, and the consumed value), not a bare failure code, so slice 1.9's top-up exchange is a pure addition.
  - Bounded state however long a run iterates: a turn's content leaves the record when the turn is recorded (slice 1.11 appends it to session memory at exactly that point), resolved effects leave with it, and acceptance reserves `AGENT_RUN_STATE_GROWTH_RESERVE_BYTES` of growth headroom so a run the entity admits can never be unable to record the turn it was created to take.
  - Terminal fencing and quiesce, enforced on every path (specification 8.7). A failed effect winds the run down the way a requested cancellation does: it fences further dispatch but stays non-terminal while sibling effects are outstanding — their results are recorded, never refused as `run-terminal` — and it never overwrites the cancellation reason an operator already recorded. A result proposal awaiting the task's decision counts as outstanding work too, so a cancelled run quiesces until the decision settles instead of being resurrected by a late rejection or left holding an accepted result under a cancelled status; acceptance wins that race, because the task durably completed on the result. A decision this binary cannot decode is refused *before* the exchange settles (`AgentExchangeParticipant::check_settle`) and stays outstanding for re-drive — a rolling upgrade no longer terminally fails runs whose tasks hold valid decisions. A replayed command whose transition already committed re-drives the settle pass it still owes before answering `Duplicate`, so the documented retry contract can unstick a run lost between committing and dispatching. An incoming model turn's schema version is checked against the run's policy where it enters, never after it is committed where recovery would fail closed forever. Wall-clock budget exhaustion reports the configured ceiling and the elapsed time, like every other dimension, and bounded run details truncate at a char boundary rather than panicking on multi-byte UTF-8. The stale-generation refusal code both entities share is the exported `AGENT_TASK_REFUSAL_STALE_GENERATION` constant.
  - `rakka_agent::testkit` gained `ScriptedDispatcher`, which plays the dispatcher's role rather than shortcutting it — it reads the effects the run committed, does the scripted work, and returns each outcome as a durable result command, memoized on the effect id so re-invoking an effect whose result was lost returns the same answer; `InProcessRunEntityTransport`; `CrashingStateStore` and `CrashPoint`, which kill an entity's owner at an exact durable write on either side of the compare-and-set; and `DeferredExchangeRouter`, the in-process late binding for two entity classes that exchange with each other.
- `rakka-agent` model adapter, deterministic test adapter, and Rig feature:
  - `AgentModelAdapter`: the Rakka-owned, provider-neutral model contract. It converts an `AgentModelRequest` — an immutable context-snapshot reference, the model profile and sampling a settings revision selected, and the turn number — into a bounded `AgentModelTurn`, and turns a provider response into that same bounded turn. The durable loop, the effect model, and the testkit depend on this trait and nothing else; a provider client, stream, open request, or credential value is never durable state, and the versioned turn is the only durable format for what a model produced. The context snapshot stays an opaque versioned reference until slice 1.11 gives it `MemoryContextSnapshot` content.
  - `AgentModelRetryPolicy`: the explicit, deployment-chosen policy that governs whether a model call is retried after an ambiguous worker loss — there is no implicit retry, because every attempt is billed. It carries the effect safety class (default `ReadOnly`) and a bounded attempt count, is declared by the adapter, and is validated where a policy enters — the adapters' fallible `with_retry_policy` builders, `read_only`, and deserialization all refuse a policy that would auto-retry a non-idempotent call after ambiguity or permit zero attempts (specification 11.4); slice 1.7's effect machine additionally enforces it at dispatch.
  - `DeterministicModelAdapter`: the deterministic test adapter of specification 10.4, implementing the trait without the `rig` feature. It scripts turns in order or conditioned on the turn number, produces them synchronously at the future's first poll — a call built and dropped unpolled consumes nothing, exactly like a provider call never made — and exercises the *same* durable effect path a provider does rather than invoking the loop around persistence. `ScriptedDispatcher` now produces its model turns through an `AgentModelAdapter` and is generic over it, so a scripted turn travels the exact path a real one travels; an adapter error — a provider failure, or a turn that cannot be bounded — surfaces as a failed effect, and answers are memoized on the effect id *and its dispatch generation*, so a re-invocation replays the recorded answer while a later generation (a genuine retry) reaches the adapter again.
  - The `rig` feature: `RigModelAdapter` wraps any Rig `CompletionModel` and implements the Rakka-owned trait, mapping a provider `CompletionResponse` onto a bounded turn — assistant text to text (separate blocks newline-separated), a call to the result tool (`submit_result` by default) to the typed result proposal, and any other tool call to a tool-call request. The result tool is declared on every completion request the adapter builds, so a real provider can actually call it; resolved `top_p` sampling is forwarded through Rig's provider parameters; billed tokens are recovered from the provider's reported total so cached and reasoning tokens are charged exactly once; a response proposing two results is refused as ambiguous rather than silently keeping the last; colliding provider call ids (rig's Gemini conversion reuses the function name) are disambiguated so every tool result stays correlated to its request; and a response carrying only content the durable turn does not record (reasoning, images) fails the mapping instead of committing an empty turn that burns billed iterations. `rig-core` is pinned exactly (`=0.37.0`) with default features off, and the pin and its compatibility review are properties of the feature: no Rig type appears in the non-`rig` public API or in persisted state, and a Rig upgrade never changes the adapter trait, the core domain types, or the persisted turn. `ScriptedCompletionModel` is a deterministic stub provider so the Rig adapter can be driven without a network, credentials, or a provider account; `returning_result_as` scripts a renamed result tool.
  - One scripted model turn runs end to end through the durable effect path under `--no-default-features`, and the same test passes under the `rig` feature against the stub provider; the adapter is the only thing that differs, and both converge on the same completed run.
- `rakka-agent` effect model and dispatcher integration:
  - The full durable effect intent on `AgentRunEffect` (specification 11.1): identity and generation, the full `AgentEffectSafety` record — `ReadOnly`, `Idempotent { external_key }`, `Reconcileable { protocol }`, `NonIdempotent` — the canonical argument digest, the settings revision, the per-attempt timeout, and the logical credential *binding*, never a resolved value. `AgentEffectSpec` is the class-level declaration a registration supplies, validated wherever it enters: a spec that would auto-retry a non-idempotent effect, permit zero attempts, or claim reconcilability without naming its protocol can neither be constructed nor loaded. `AgentEffectPolicies` is the interim registration surface on the run entity (deployment configuration keyed by tool; slice 1.8's registry replaces the map without changing the record), and its defaults fail safe: a model call is one read-only attempt, and an unclassified tool is non-idempotent. The external idempotency key derives from the effect identity *and generation*, so every retry of one generation hands the target the same key and a newly authorized invocation presents a fresh one.
  - The effect status machine with generations (specification 11.3). The run-side record owns `Pending`, `Ready`, and the five terminal outcomes (`Succeeded`, `Failed`, `Exhausted`, `Indeterminate`, `Cancelled`); the dispatch layer's durable records own `Started` (outbox `Dispatching` plus the fleet lease and fencing token) and `RetryScheduled`. `Pending` is load-bearing: an effect is handed to the sink only after the transition that marked it `Ready` committed, so a `Pending` effect has provably never reached the outbox and a cancellation may fence it in place — in the same compare-and-set as the cancellation's acceptance — with nothing abandoned. `Indeterminate` is terminal for one generation but blocks the run's settlement: the run parks in `WaitingForReconciliation`, automatic dispatch eligibility for the effect is revoked at both durable layers, and only the explicit `AgentEffectResolution` decision — `ConfirmedExecuted` with the established outcome, or `ConfirmedNotExecuted`, never a generic retry — resolves it. `ConfirmedNotExecuted` mints a *new* effect generation: a fresh dispatch ticket, attempt budget, and external key under the same identity, so the ambiguous original is never mutated back into a routine attempt, and a late result from a superseded generation is refused by the run's own fence (`run-stale-effect-generation`).
  - `AgentRunEffectDispatcher` in `rakka_agent::dispatch`: the durable dispatch pipeline over the run's agent-workflow outbox and the dispatcher fleet. Each generation's dispatch ticket is an outbox row deduplicated on the generation-qualified ticket id with its retry budget aligned to the intent's attempt bound; a worker claims the fleet lease and writes the outbox's durable `Started` before any external call; credentials are resolved only inside the bounded attempt through `AgentEffectCredentialResolver` (reusing the substrate's redacted `AgentEphemeralCredential`) and dropped with it; and every result command carries effect id, generation, attempt, and the claim's fencing token (specification 11.4). Crash and timeout recovery reads the outbox row as the ambiguity marker and applies the safety class (specification 11.5): a row never marked `Dispatching` redispatches safely for every class; an ambiguous read-only or idempotent attempt retries under the intent's bounded budget (the idempotent retry reusing its external key); an ambiguous reconcileable attempt queries its `AgentEffectReconciler` protocol before any retry and retries only when proven absent; and an ambiguous non-idempotent attempt produces exactly one durable `Indeterminate` outcome and is never automatically re-invoked. A stale ticket — one whose run-side intent was resolved, superseded, or fenced — settles as cancelled without invoking anything.
  - Cancellation fencing at the effect layer (specification 8.7). Accepting a cancellation fences provably-unsent effects in the same transition and stops the flush; the pipeline cancels tickets that provably never started (planting a tombstone row where a laggard flush might still write one), lets attempts already at the dispatch layer settle truthfully, and treats an ambiguous consequential attempt under cancellation exactly as above — so a cancelled run's ambiguous non-idempotent effect keeps the run nonterminal in `WaitingForReconciliation`, and terminal cancellation is projected only after the outcome is explicitly resolved (scenario 57's effect half). Failed-effect wind-downs fence their unsent siblings the same way.
  - Recovery scenarios 5 through 9 are proven over the real pipeline with dispatcher loss injected at every durable boundary — before `Started`, after `Started`, after the external commit, and after result delivery — via `rakka_agent::testkit`'s new `KillSwitchProbe`, `RecordingToolExecutor` (whose invocation log is the external system: commit counts and the idempotency keys the target saw), `ScriptedReconciler`, `ScriptedCredentialResolver`, `InProcessRunResultDelivery`, and `SharedAtomicWorkflowClock` for deliberate lease expiry. A first rough per-turn measurement over the integrated path (one clean model turn: 8 run-store compare-and-sets, 3 workflow-store writes, ~6ms wall on in-memory stores in a debug build) is recorded by `per_turn_durable_write_count_and_latency_measurement`; slice 1.14 formalizes the budget.
- `rakka-agent` tool registry, tool authority, and guardrail baseline:
  - `AgentToolRegistry` in `rakka_agent::tools` (specification 11.7): the deployment's registry of dispatchable tools, each an `AgentToolBinding` over a bounded, model-visible `AgentToolDescriptor` — stable name, monotonic descriptor version, kind (`Function`, `Workflow`, `Process`, `RemoteMcp`, `Retrieval`, `Environment`, `AgentCoordination`), bounded description, input/output schema references, optional inline parameter schema, and declared result behavior. The binding carries the trusted deployment authority: safety class, scoped capabilities, credential binding class, execution-policy routing, attempt bound, reconciliation protocol, per-attempt timeout, required guardrail stages, and checkpoint requirement. A tool registered without a declaration is *unclassified* and fails safe as one non-idempotent attempt. `AgentToolRegistry::effect_policies` projects the bindings onto the run's commit-time `AgentEffectPolicies`, so the registry is the single source the loop stamps intents from and the dispatcher revalidates against; `model_visible` computes the descriptors a model may be shown (registered, declared by the envelope, not revoked) — visibility that carries no dispatch authority.
  - The four authority layers of specification 11.8, each only able to narrow the one above it: descriptor (model-visible), binding (deployment-authorized), `AgentRunEffect` (the exact durable intent, which now also persists its application-owned `AgentExecutionPolicyRef` and echoes it on the dispatch ticket), and `AgentDispatchGrant` — the current authorization to execute one exact intent, binding tenant/goal/task/agent/run, effect id and generation, descriptor version and schema digest, target and canonical argument digest, safety class, the definition/settings/setup/guardrail revisions it validated, capabilities, credential binding, execution policy, expiry, and an allowed use count aligned to the intent's attempt bound. Model output structurally cannot widen anything: a tool-call request carries only a call id, a tool name, and arguments, and everything else resolves from durable definition, setup, and deployment data.
  - `AgentDispatchAuthority` is a *required* collaborator of `AgentRunEffectDispatcher`: every attempt is authorized before durable `Started`, and the grant is revalidated against the exact intent — there is no permissive default, because a pipeline that could skip the check would be the universally privileged worker specification 16 forbids. `AgentEntityAuthority` backs the gate with the agent entity's durable state, so a suspension or an immediate-safety settings revocation (a revoked tool or credential binding) accepted by the entity is honored by the very next dispatch attempt with the agent fully passivated, and the slice 1.2 setup/settings envelope is enforced at dispatch: an unregistered tool, an undeclared tool, a tool the run's setup narrowed away, a downgraded safety class, a mismatched credential or execution policy, a missing checkpoint grant, and an unroutable execution policy all leave the call undispatchable with a stable reason code (scenarios 44 and 54). The intent-layer revalidation also holds the reconciliation protocol and per-attempt timeout to the binding's declaration, and the settings' guardrail-policy selection — the third immediate-safety field — refuses dispatch (`guardrail-policy-mismatch`) unless the deployed chain provably implements it. A transient refusal — a suspension — spends nothing: the ticket is deferred at the fleet with the outbox row untouched, so no attempt burns, no `Failed` row can be misread by recovery as a possibly-executed reconcileable attempt, and a resumed agent's next attempt rechecks and proceeds even under the fail-safe single-attempt defaults. A definitive refusal settles the generation as failed with nothing invoked — unless a prior attempt of the generation may already have executed (the recovery retry of an ambiguous idempotent loss), in which case the generation parks `Indeterminate` under the refusal's code, preserving the ambiguity an operator must resolve. Because runs do not yet carry their setup reference, the gate resolves setups per claimed run through `AgentRunSetupResolver` — never a fixed per-worker setup a fleet-wide claim batch would misapply to other runs. The authority also resolves the turn-bound settings of specification 7.2 at dispatch: the granted model call carries the profile and sampling the *current* settings revision selects, validated against the definition and setup envelopes. Grants are minted and revalidated per attempt, valid through their expiry instant; the TTL bounds a grant a holder retains, which no shipped path does before slice 1.10's durable checkpoint grants.
  - The guardrail baseline in `rakka_agent::guardrails` (specification 16): versioned, ordered `AgentGuardrailChain` stages with the bounded outcome set — `Allow`, `Block`, `Transform`, `ReportOnly`, `RequireCheckpoint` — stable reason codes, and protected evidence references. Stages declare the boundaries they run at, and presence in the chain is never coverage: a boundary-less stage is refused at registration (`guardrail-stage-unbound`), and a required stage bound only to boundaries the caller does not evaluate refuses dispatch (`guardrail-stage-unevaluated`) rather than satisfying an envelope's mandatory set while never running. This slice evaluates the tool-request and model-request boundaries before every attempt's durable `Started` (`AGENT_EVALUATED_GUARDRAIL_BOUNDARIES`), and the remaining declared boundaries — model/tool response, A2A ingress/egress, memory ingress — gain their evaluation points, and with them their coverage, from the slices that own those flows. A stage is evaluated against an `AgentGuardrailContext` naming the boundary, the run scope, and — at the tool boundaries — the tool being called, so per-tool and per-tenant policy is expressible; only the content a transform may rewrite is passed as content, so identity is readable but structurally unrewritable. Evaluation is a pure synchronous fold, so a stage physically cannot introduce I/O into a durable transition: a block short-circuits and wins, carrying its evidence reference into the refusal detail; transforms compose deterministically and are recorded with their reasons (the tool boundary bounds transform content to what a call can actually carry, so an oversized transform is one deterministic block wherever it is caught); report-only findings accumulate and, like applied transforms, surface on the dispatcher's trace; and a checkpoint requirement fails closed until the slice 1.10 checkpoint runtime can satisfy it (a transform at the still-synthesized model-request boundary also fails closed, `guardrail-transform-unsupported`, rather than being silently ignored). A deployment-mandatory stage cannot be removed by a definition, setup, or settings update — `narrowed` refuses the removal, and a narrowed chain must carry its own revision, because a different stage set is a different evaluation — and an envelope that requires a stage the deployment's chain cannot run refuses dispatch (`guardrail-stage-missing`) rather than running without the guardrail the definition promised. A guardrail-transformed tool call executes the transformed arguments while the intent's argument digest stays bound to what the run committed, and the transform is provably identical on every attempt of the generation: each committed intent pins the chain revision of the policies it was stamped from (`AgentToolAuthority::effect_policies`), and the pipeline refuses an attempt (`guardrail-revision-mismatch`) whenever a transform would decide the payload — or any retry follows a possibly-delivered attempt — under a chain that no longer matches the pin, so one external idempotency key can never carry two different payloads.
- `rakka-agent` hierarchical escrow budget ledger (specification 9.7): `AgentEscrowLedger` is a component of the owning entity's own durable state, so an allocation, a settlement, and a return commit in the same compare-and-set as the transition that decided them — one writer, no distributed transaction, oversubscription structurally impossible. The dimensions split in two: *conserved* quantities (iterations, model calls, tool calls, effects, effect attempts, tokens, cost) are escrowed — debited from a parent, held by a child, returned unused — while wall-clock and concurrency are inherited limits rather than quantities and are narrowed down the hierarchy rather than debited. A task holds the escrow for its runs (`AgentTask::escrow`) and debits every run it assigns inside the assignment transition, carrying the `AgentBudgetGrant` on the assignment command; a run whose escrow the task cannot afford is refused (`task-budget-unavailable`) and stays assignable, so an earlier generation's settlement can restore the headroom. Every effect a run commits is reserved from its own ledger before dispatch, folded into the same all-or-nothing per-turn charge (`reserve_model_turn`, `reserve_tool_turn`): one durable effect and its whole attempt bound, plus a concurrency-ceiling check, so a run cannot start work it could not afford to finish retrying, and a fan-out wider than the concurrency ceiling never commits. When a generation resolves, `settle_effect` consumes the attempts that actually reached `Started` — a `Started` attempt that becomes `Indeterminate` still consumes its attempt — and releases the retries the generation did not use (scenario 52). A terminal run hands its escrow back in two ordered exchanges — settle what it consumed, then return what it did not — sequenced by its durable `AgentRunSettlementStatus` so a loss between them re-drives the same operation. Settlement precedes return, and the ledger refuses a return for a child that has not settled: releasing the whole allocation before knowing what was spent would hand back budget already burned. Each command is deduplicated on the child's escrow record rather than the exchange journal's bounded ring, so a replay that outlived the window still credits the parent exactly once, and over-consumption (a final turn billing past its allocation) is recorded and saturates the parent's headroom at zero rather than being rejected — the next charge is where a spent budget refuses (scenario 61, `tests/escrow_ledger.rs`). A run that exhausts a ceiling does not fail on the spot: it parks with the structured exhaustion (`AgentPendingTopUp`, status stays `Running` because a pending exchange is the run's own outbox, not a residency wait) and asks its parent for more through a deduplicated `BudgetAllocation` exchange, committed to the run's journal by the transition that hit the ceiling and drained by the same courier. The parent's grant is an ordinary parent-local decision under its own ceilings; a grant that adds room in the exhausted dimension resumes the run exactly where it parked — the failing charge is all-or-nothing (`reserve_model_turn`, `reserve_tool_turn`), so re-attempting double-counts nothing — while a grant of nothing (the honest answer when the parent has nothing left) stops the run with its *original* exhaustion rather than parking forever, and because each grant strictly reduces the parent's headroom the asking always terminates. Only conserved dimensions park to ask: a wall-clock deadline or a concurrency ceiling is not a quantity a parent can grant, so a run that crosses one stops with the structured reason rather than re-parking on a ceiling that would never move. Enforcement is proven end to end — a real dispatched effect debits `effects` and `effect_attempts`, an unaffordable turn is denied, an over-deadline run stops, concurrent allocations cannot oversubscribe a parent, the whole round trip (allocation, reservation, settlement, return) converges under owner-crash injection at every durable write on both sides of the compare-and-set without double-debiting or double-crediting, and an unattended (`BoundedAsync`) task is refused without an admission and runs once admitted (`tests/escrow_ledger.rs`, `tests/autonomy_admission.rs`; scenarios 52, 53, 61).
- `rakka-agent` inter-entity choreography: an entity's `accept` of a delivered exchange now makes *local* progress only — it cranks its own loop and dispatches effects, or decides an assignment freed budget permits and flushes owed history — and commits any onward cross-entity exchange to its durable journal without delivering it. Draining that journal is the courier's job (a command's settle pass, a recovery sweep, a fault-injection pump), never a synchronous step inside a delivery. This is the durable-outbox discipline made uniform, and it is what keeps the choreography acyclic: the initiator of the exchange being accepted is mid-delivery to this entity, so driving an owed exchange back to it from inside `accept` would re-enter a transition whose reply has not settled — a terminal run owing its task a settlement, and the task re-driving that run's still-outstanding assignment, would otherwise recurse without bound. Every cross-entity outcome still converges through the bounded-iterative courier exactly as before.
- `rakka-agent` autonomy admission (specification 7.4): `AutonomyAdmissionDecision` is the immutable, fail-closed record that decides whether an unattended class (`BoundedAsync`, `Continuous`) may run at all — it carries its operation classes, the definition/settings/setup revisions it evaluated, the evaluator principal or service, the requirements it verified, bounded constraints, and an optional expiry, and never a resolved credential. An authorized evaluator authors it outside Rakka and submits it as an ordinary deduplicated `Admit` command; the entity is not a rubber stamp — it verifies every requirement the definition itself answers (`verify`) and refuses a decision naming revisions the agent is no longer on (`stale-admission-revision`). An unattended class that does not name every requirement is not a partial admission, it is not an admission; `Retract` returns the agent to the fail-closed default (`admission-missing`), indistinguishable from never-admitted at every enforcement point. Widening is *derived, never tracked*: assignment re-derives the decision against the definition now in force (`admits_definition`) rather than trusting a recorded answer, so a definition published since the admission that widened its authority envelope stops assignment (`admission-widened`) without anything having had to notice the update. The derivation is *both* the envelope narrowing **and** the structural requirements `verify` checks: a republish that dropped a required approval, authorization, or escalation policy — a policy reference is not part of the authority envelope, so it is not an envelope widening — is refused (`admission-requirement-regressed`) even though the envelope did not widen, closing a fail-open where a stale admission could otherwise admit unattended work whose verified guarantees the current definition no longer provides. Because enforcement derives from the current definition, publishing a new definition deliberately does not retract the admission: fail-closed is a property of the derivation, not of a hook every future call site must remember to fire.
- `rakka-agent` durable checkpoints and HITL — the checkpoint substrate and its digest-bound grant (specification 12; scenarios 3, 11, 12, and the reconciliation half of 57):
  - `AgentCheckpoint` in `rakka_agent::checkpoints` is the durable, schema-versioned checkpoint record of specification 12.2, in the three kinds `Approval`, `SecurityAuthorization`, and `IndeterminateEffectReconciliation`. It binds the exact effect intent (id, generation, target, argument digest, safety class, logical credential binding) and carries the tenant/goal/task/agent/run/delegation identity, bounded non-secret prompt/decision summary, allowed decisions, required roles/capabilities and policy reference, settings/definition revisions, creation/SLA/expiration/escalation timestamps and target, immutable context/evidence and audit references, and creator/resolver principals — never resolved credential material. It is plain durable state that round-trips through serialization, so a run passivates behind an open checkpoint and resolves it on the next command with no live execution task.
  - Grant binding is cryptographic and exact (specification 12.3). `AgentContentDigest` gained a `Sha256` algorithm — a pure-safe-Rust FIPS 180-4 implementation, no new dependency, pinned to the standard vectors — because the FNV fingerprint the effect carries is explicitly not a security boundary. An `Approve`/authorization resolution issues an `AgentCheckpointGrant` bound to the SHA-256 digest of the effect's canonical arguments, plus scope, effect id and generation, target, safety class, settings revision, logical credential binding, resolver, expiry, and allowed use count. `AgentCheckpointGrant::validate_for` recomputes the cryptographic digest from the intent and fails closed on a changed argument (`checkpoint-argument-digest-mismatch`), a superseded generation or target (`checkpoint-grant-intent-mismatch`), a changed credential binding, a spent use count, an elapsed expiry, or a non-cryptographic digest — so a changed effect digest invalidates a stale approval (scenario 12).
  - The two authority checkpoint gates that previously failed closed unconditionally — the `checkpoint_required` binding and a guardrail `CheckpointRequired` disposition — now accept a valid digest-bound grant carried on `AgentAuthorityContext::with_checkpoint_grant`, revalidated against the exact intent and the actual 1-based attempt number before dispatch (`AgentDispatchAuthority::authorize` and `AgentToolAuthority::authorize` receive the attempt the pipeline is about to make, so a grant's allowed use count bounds retries: a spent grant does not cover the next attempt), and still fail closed with `checkpoint-required` (or the specific grant-invalidation reason) when no grant binds. Because revocation is an immediate-safety settings check that runs before the checkpoint gate, an immediate tool or credential revocation refuses the next dispatch even under a still-valid approval (scenario 13). The `AgentEntityAuthority` gate sources the grant the run holds and passes it through the same revalidation (see the run-side wave below).
  - Run-side park/resume and durable SLA timers. A tool the deployment marks checkpoint-required carries that requirement on its projected `AgentEffectSpec` and durable `AgentRunEffect`, so when the loop would schedule it the run opens an `Approval` `AgentCheckpoint` bound to the exact effect and parks in `WaitingForApproval` — the checkpoint and the effect commit in one transition, and `dispatch_effects` never hands a gated effect to the sink without a grant. The run passivates behind the wait with no live task and resumes only on a durable command (scenario 3). A new `AgentRunEntityCommand::ResolveCheckpoint`, deduplicated on its operation id, applies an authenticated decision: an `Approve`/`Grant` records the digest-bound `AgentCheckpointGrant` on the run's loop state and resumes it, so the next dispatch pass finds the grant, the real `AgentEntityAuthority` revalidates it against the exact intent, and the tool executes; a duplicate submission returns the original outcome and never resumes the run twice (scenario 11); a `Deny` fails the gated effect's generation (`checkpoint-denied`). `WaitingForApproval`/`WaitingForAuthorization` now fence the loop crank in `permits_progress`, and a resolved grant leaves with its effect. `AgentRunEntityCommand::FireCheckpointTimers` applies the durable SLA and expiration deadlines a deployment configures through `AgentCheckpointSla`: an overdue checkpoint escalates and stays open, an expired one is denied (`checkpoint-expired`) and the run winds down — a timeout never auto-approves sensitive or non-idempotent work ([specification 12.6](docs/plans/rakka-agent/spec.md)). Covered by `tests/checkpoint_run.rs` and the end-to-end grant test in `tests/tool_authority.rs`. A cryptographic argument digest is added to `AgentDigestAlgorithm::Sha256` for the grant binding (see above); the guardrail-driven checkpoint requirement discovered dynamically at dispatch remains a dispatch-time concern rather than a commit-time park.
  - The reconciliation decision set is exactly specification 12.5 — `ConfirmedCompleted`, `ConfirmedNotExecuted`, `Compensate`, `Escalate`, `AbandonAndFail` — with no plain `Retry`: `ConfirmedCompleted`/`ConfirmedNotExecuted` map to the effect layer's `AgentEffectResolution` (only `ConfirmedNotExecuted` authorizes a new generation), `Compensate` schedules an explicitly defined compensation (`AgentCompensationRef`), `AbandonAndFail` fails the effect's generation terminally, and `Escalate` keeps the checkpoint nonterminal so a later decision converges it — the reconciliation half of scenario 57.
  - Every resolution is deduplicated on its decision key: a replayed decision returns the original outcome and makes no second transition, and a different decision against a resolved checkpoint is refused (`checkpoint-already-resolved`), so a duplicate human or authorization decision never resumes a run twice (scenario 11). `AgentCheckpoint::on_timer` drives SLA escalation and hard expiration from durable timestamps and can only escalate or expire a waiting checkpoint — it can never grant or approve, so a timeout on sensitive or non-idempotent work fails closed (specification 12.6). Covered by `tests/checkpoints.rs` and the checkpoint-gate tests in `rakka_agent::tools`.
  - The `SecurityAuthorization` runtime path (specification 12.4). A tool binding may declare `with_authorization_required`, projected through `AgentEffectSpec` onto the durable `AgentRunEffect`, so the run opens a `SecurityAuthorization` checkpoint bound to the exact effect and parks in `WaitingForAuthorization` — the same durable wait, dedup, timer, and passivation substrate as an approval, with the resolution supplying the capability or logical credential binding the effect needs (a reference only, never secret material). The dispatch authority enforces the *kind*: an authorization-required tool refuses without a grant (`authorization-required`) and refuses an approval-kind grant — a human approval can never stand in for a security authorization — so the authorization sub-case of scenario 3 and the authorization flavor of scenario 11 are now demonstrable (`tests/checkpoint_run.rs`, the kind-gate test in `rakka_agent::tools`).

An `Indeterminate` outcome opens an `IndeterminateEffectReconciliation` checkpoint in the same transition that recorded the ambiguity, so the wait carries the full specification 12.2 surface — decision set, dedup key, SLA escalation, roles — and the whole 12.5 decision set reaches the run through `ResolveCheckpoint`: the confirming decisions flow through the shared effect-resolution core (with `ConfirmedNotExecuted` still minting exactly one new generation under a fresh attempt reservation — and re-parking a checkpoint- or authorization-gated effect's new generation behind a fresh checkpoint of the matching kind, since the grant that authorized the ambiguous generation binds that generation exactly), `Escalate` keeps the wait, and `AbandonAndFail` fails the generation (`reconciliation-abandoned`) and winds the run down under whatever wind-down reason was already on record. A reconciliation checkpoint never hard-expires — expiry would fabricate a definitive failure for an effect whose outcome is unknown — and a run cancellation cancels only approval-family checkpoints, so the parked ambiguity stays resolvable and terminal cancellation still projects only after its decision (scenario 57). The ambiguous generation settles as `AgentRunEffectStatus::Compensated`, the run winds down under a new `AgentRunTerminalReason::EffectCompensated`, and a new `AgentRunEffectRequest::Compensation` effect — carrying the `AgentCompensationRef` and the compensated generation, reserved against the run's budget like any re-authorized attempt — is committed *after* the wind-down fence and is the one kind of effect a winding-down run still flushes to the sink; the run reaches its terminal status only after the compensation's own outcome settles. - `rakka-agent` agent-private long-term memory (specification 13.1, 13.3; slice 2.1, the first M2 slice — the private halves of scenarios 15, 16, and 18): the interface-only `AgentPrivateMemoryStore` declared by slice 1.11 is now a real subsystem. The record carries the full 13.3 shape — schema version with fail-closed load, the compare-and-set `revision`, structured `AgentPrivateMemorySource` provenance (run/effect/entry, never authority), content-free `MemoryEmbeddingRef` metadata (slice 2.2 fills the vectors), `MemoryRetention` (persistent or expiring), the auditable `MemoryTombstone` stub state, and policy/audit references — reshaped in place at schema version 1 under the unreleased-branch rule, since no released writer ever persisted the earlier shape. Writes resolve open decision 1's M2 half: a create is idempotent on its operation id and a replay answers the *original* result from the store's operation ledger even after later updates, an update is a compare-and-set on an explicit `PrivateMemoryExpectation` (a blind overwrite is unrepresentable), and a stale writer is refused (`memory-revision-conflict`) rather than overwriting a concurrent run's memory (scenario 15). Deletion is final in both directions: tombstone and delete are their own idempotent operations that erase the ledger's earlier payloads for the memory, so a replayed old write fails closed (`memory-operation-erased`) instead of resurrecting withdrawn content, while the tombstone's content-free stub stays visible in scope — digest and provenance intact — because the withdrawal itself is auditable. Consolidation is the same effect naming an `AgentMemoryConsolidationTarget`: a compare-and-set update of exactly one memory from exactly one entry, whose stale expectation settles the generation `Failed` without a write. - `rakka-agent-postgres`: the pgvector retrieval adapter (`PgvectorPrivateMemoryRetriever`).   (specification 13.4, 13.6; slice 2.3 — the graph halves of scenarios 16 and
  18). Agents append provenance-bearing claims scoped
  `(TenantId, KnowledgeSpaceId)` — never overwrite communal truth — and every
  claim is born `Proposed` structurally: `Claim::new` takes no trust
  parameter, the only path to a non-`Proposed` claim is restoring a persisted
  record whose `Proposed ⇔ zero-transitions` coherence invariant is
  re-validated on every load, and the store's append door refuses anything
  else (`claim-append-not-proposed`), which resolves open decision 3. Open

  injective scope key, so a cross-tenant graph is unrepresentable rather than
  merely disallowed. Claim identity derives from the append operation id
  (conflicting claims must coexist, so the statement cannot be the identity),
  which is what makes a replayed append converge on the same claim. Every
  identity derivation (append key, transition key, claim id) digests with
  sha2-256 rather than the default FNV fingerprint — salted domains stop a
  discriminator from being spelled as another domain's input, but only a
  collision-resistant digest stops one from being searched for a collision
  within a domain, and identity here decides whose write a replay answers;
  because the append door re-derives, the algorithm is part of the durable
  contract rather than an implementation detail. The derivation is likewise an

### Changed

- Workspace MSRV is raised from Rust 1.80 to Rust 1.85, required by the published A2A SDK crates used by the Phase 0 clustered sharded A2A agents example.
- The workspace `axum` dependency is upgraded from 0.7 to 0.8. `axum` types appear in the `rakka-http` public API, and axum 0.8 replaces the `/:param` route syntax with `/{param}` and changes websocket text/close payloads to `Utf8Bytes`.
- Workspace crates now share release metadata and internal path dependencies include explicit versions for packaging.
- CI separates required validation from optional PostgreSQL and local Kubernetes integration jobs.
- Historical implementation plans now live under `docs/plans/` instead of the product-doc root.
- `rakka-workflow` outbox entries support a terminal `Cancelled` status: `DurableInbox::record_outbox_cancelled` settles an undelivered entry before dispatch, cancelled entries are never due again, and compaction reclaims them like other terminal entries.
- Agent dispatcher cancellation is durable end to end: `AgentDispatcherWorker::cancel_run_dispatches` settles cancelled effects at the outbox layer, in-flight entries carry a typed `cancellation_requested` flag that blocks re-claiming after lease expiry, and worker refresh finalizes expired cancellation-requested entries as cancelled instead of redelivering them.
- Agent dispatch target classification only honors `target_class` attribute and target-type refinements that are compatible with the effect kind, so a mislabeled effect can no longer be routed to a dispatcher that deterministically rejects it.
- Agent autonomy policy classification (`AgentAutonomyTargetClass::for_effect`) is derived from the dispatcher's `AgentDispatchTargetClass::classify`, removing the name-substring webhook/push heuristics so policy admission and dispatch routing always agree on an effect's class.
- `rakka-persistence-postgres` applies its migration under a session advisory lock (`MIGRATION_LOCK_ID`), so concurrent migrators no longer race PostgreSQL's system catalogs. `CREATE TABLE IF NOT EXISTS` is not atomic against a concurrent creation of the same table: two nodes starting together against a fresh database both saw the tables missing, both proceeded, and the loser failed to start with `duplicate key value violates unique constraint "pg_type_typname_nsp_index"` instead of the no-op the `IF NOT EXISTS` reads like. The guard matches the one `rakka-a2a`, `rakka-sharding-postgres`, and `rakka-agent-postgres` already applied to theirs — this crate, the oldest of them, was the one still unguarded — under a lock id distinct from every sibling's so the subsystems' migrations do not serialize against each other. The race is invisible once the tables exist, which is why a reused developer database never showed it; a DSN-gated test now races four migrators in a private schema.
